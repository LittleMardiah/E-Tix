   - Validate ticket_id matches request ticket_id (anti-tamper)
   - Ticket status transition: CONFIRMED → USED
   - INSERT ticket_scans (scan_status = VALID/INVALID/ALREADY_USED,

   - Lookup ticket by fallback_pin
   - Validate fallback_pin_used = FALSE (single-use)
   - Mark fallback_pin_used = TRUE + fallback_pin_used_at = NOW()
   - Status transition: CONFIRMED → USED
   - INSERT ticket_scans (scan_method = PIN)
   - Idempotency via scan_id

✅ Offline Sync Flow (POST /gate/sync):
   - Batch input max 500 scans (FLAG #3)
   - Body max 1MB (BodySizeLimit)
   - Idempotency per scan_id (ON CONFLICT DO NOTHING)
   - Conflict resolution: earliest scanned_at wins, tie-breaker smallest scan_id
   - Loser scans marked as ALREADY_USED + response includes conflicts[]
   - Atomic per scan (transaction)

✅ Conflict Resolution (FLAG from FASE 5 / SECURITY_SPEC §8.4):
   - Multi-device offline: 2 devices scan same ticket offline
   - Winner = earliest scanned_at (deterministic)
   - Tie-breaker = smallest scan_id (lexicographic UUID ASC)
   - Loser device sees notification: "Duplicate scan detected"

3.3 FROM LOGIC_FLOW v1.4 §6 — FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

QR SCAN FLOW:

  Function ScanQR(ctx, req):
    Step 1: Auth middleware (role = gate_staff)
    Step 2: Validate scan_id (idempotency)
              - Redis SET NX scan:{scan_id} 1 EX 86400
              - If exists → return cached response (idempotent)
    Step 3: SELECT ticket BY id = req.TicketID
              - If not found → INSERT scan (INVALID) + 404
    Step 4: Verify HMAC:
              - valid, decodedTicketID = VerifyDynamicQR(req.QRData, ticket.qr_secret_key)
              - If !valid → INSERT scan (INVALID) + 401
              - If decodedTicketID != req.TicketID → INSERT scan (INVALID) + 401
    Step 5: Status branch:
              - IF ticket.status = 'USED':
                  INSERT scan (ALREADY_USED) + 409
              - IF ticket.status != 'CONFIRMED':
                  INSERT scan (INVALID) + 422
    Step 6: Valid path:
              - INSERT scan (VALID, QR, scanner_device_id, gate_id)
              - Trigger update_ticket_status_on_scan → ticket.status = USED
    Step 7: Return { valid: true, owner_name, seat, status: 'USED' }

PIN VERIFY FLOW:

  Function VerifyPIN(ctx, req):
    Step 1: Auth middleware
    Step 2: Validate scan_id (Redis SET NX)
    Step 3: Compute input_hash = input (plain — FLAG #1 FASE 5)
    Step 4: SELECT ticket BY fallback_pin = req.PIN 
            AND fallback_pin_used = FALSE 
            AND status = 'CONFIRMED'
              - If not found → INSERT scan (INVALID, PIN) + 401
    Step 5: UPDATE ticket:
              - fallback_pin_used = TRUE
              - fallback_pin_used_at = NOW()
              - status = 'USED'
    Step 6: INSERT scan (VALID, PIN)
    Step 7: Return { valid: true, scan_method: 'PIN', status: 'USED' }

OFFLINE SYNC FLOW (FLAG #3):

  Function SyncOfflineScans(ctx, req):
    Step 1: Auth middleware
    Step 2: Validate: len(req.Scans) <= 500 
              - Else → 422 UNPROCESSABLE_ENTITY
    Step 3: Body size limit 1MB (middleware)
    Step 4: Initialize counters: synced=0, duplicates=0, failed=0, conflicts=[]
    Step 5: FOR EACH scan IN req.Scans:
      a. BEGIN transaction
      b. INSERT INTO ticket_scans (
           id=scan.scan_id, ticket_id, gate_id, scanner_device_id,
           scan_status, scan_method, scanned_at
         ) ON CONFLICT (id) DO NOTHING
      c. If RowsAffected == 0:
           duplicates++, ROLLBACK, continue
      d. IF scan.scan_status = 'VALID':
           - SELECT ticket FOR UPDATE
           - IF ticket.status = 'USED':
               // Conflict resolution
               - Get winner scan (existing VALID scan for this ticket)
               - Compare scanned_at: earliest wins
               - Tie-breaker: smallest scan_id
               - Mark loser scan (current) as ALREADY_USED
               - Append to conflicts[] array
               - UPDATE our scan_status = 'ALREADY_USED'
           - ELSE (ticket CONFIRMED):
               - UPDATE ticket SET status = 'USED'
      e. COMMIT, synced++
    Step 6: Return { synced, duplicates, failed, conflicts: [...] }

CONFLICT RESOLUTION (DETERMINISTIC):

  Winner selection rule:
    1. Earliest scanned_at (ASC)
    2. Tie-breaker: smallest scan_id (lexicographic UUID ASC)

  Loser handling:
    - scan_status = 'ALREADY_USED'
    - Response includes conflicts[] with winner/loser details
    - Admin notification if conflicts > threshold (10 per batch)

POST-EVENT REPORT GENERATION:

  Trigger fires when event.status → COMPLETED.
  Flow (database trigger):
    1. CTE gate_stats: aggregate ticket_scans per gate_id
    2. CTE ticket_stats: count total / used / unused tickets
    3. CTE loyal_fans: count users with total_purchases > 1
    4. Build report_data JSONB:
         { event_id, event_name, total_tickets, used_tickets, 
           unused_tickets, no_show_rate, total_scans, valid_scans, 
           gate_utilization, loyal_customers, generated_at }
    5. INSERT INTO insights (event_id, insight_type='PEAK_TIME', 
                             title='Post-Event Report - ' || event.name, 
                             recommendation=report_data)

FEEDBACK LOOP WORKER (FLAG #2):

  Function FeedbackLoopWorker():
    ticker := time.NewTicker(24 * time.Hour)
    FOR range ticker.C:
      ProcessFeedbackLoop()

  Function ProcessFeedbackLoop():
    Step 1: SELECT events WHERE status = 'COMPLETED' 
            AND updated_at > NOW() - INTERVAL '48 hours'
    Step 2: FOR EACH event:
      a. IF NOT EXISTS insight (event_id, 'GATE_STAFFING'):
           - Analyze gate_utilization historical
           - Generate staffing recommendation
           - INSERT insight
      b. IF NOT EXISTS insight (event_id, 'BOT_BLACKLIST'):
           - Analyze INVALID scan patterns (per IP)
           - Auto-INSERT into blacklist for suspicious IPs
           - INSERT insight (type=BOT_BLACKLIST)
      c. IF NOT EXISTS insight (event_id, 'PRICE_RECOMMENDATION'):
           - Analyze no_show_rate + resale activity
           - Generate pricing recommendation
           - INSERT insight
      d. IF NOT EXISTS insight (event_id, 'PEAK_TIME'):
           - Already inserted by trigger (post-event report)
           - Skip if exists
    Step 3: Log {events_processed, insights_created}

QR VERIFY HELPER (shared dengan FASE 5):

  Function VerifyDynamicQR(qrToken, secretKey):
    Step 1: Decode base64 → split "|"
    Step 2: Parse ticketID
    Step 3: currentBlock = NOW().Unix() / 30
    Step 4: FOR block IN [block-1, block, block+1]:
              payload = ticketID + "|" + block
              expected = HMAC-SHA256(secretKey, payload)
              IF hmac.Equal(signature, expected):
                RETURN (valid=true, ticketID)
    Step 5: RETURN (valid=false, error)

3.6 FROM SECURITY_SPEC v1.4 §8.4 — OFFLINE QR + CONFLICT RESOLUTION
────────────────────────────────────────────────────────────────────────────────

OFFLINE GATE QR VALIDATION:

  Mekanisme:
    1. Saat sync awal, device simpan HMAC key temporer di secure storage
    2. Saat offline, device verifikasi HMAC lokal (tolerance ±30s)
    3. Scan valid → queue lokal dengan scan_id UUIDv4
    4. Sync via POST /gate/sync (batch max 500)
    5. Key local TTL, dihapus setelah event atau logout

CONFLICT RESOLUTION (multi-device):

  7a. Jika ticket_id yang di-sync offline sudah berstatus USED 
      (dipindai di gate lain secara offline):
      a. Record pindaian pertama = USED
      b. Record pindaian kedua = ALREADY_USED 
         (sesuai scan_status_enum DATABASE_SCHEMA v2.9)

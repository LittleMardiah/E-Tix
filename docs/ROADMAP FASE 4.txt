   - POST /webhook/payment                 — Signature validation (header OR body)

✅ Payment Modes:
   - SPLIT: N payment_obligations (1 per member, with seat_position), 
            each member pays own amount
   - BULK:  1 payment_obligation (leader pays all), seat_position = NULL

✅ Payment Gateway Integration:
   - Provider: Midtrans Sandbox (dev), MidtransPaymentAdapter
   - Abstract interface: PaymentGateway (charge, refund, payout)
   - Charge API → get external_transaction_id + payment_link
   - Webhook receiver: signature validation via adapter (dual-source, see §8.3)
   - Midtrans signature formula: SHA512(order_id + status_code + 
     gross_amount + ServerKey) — di dalam adapter, bukan di domain layer

✅ Idempotency (L1 + L2):
   - Client-provided X-Idempotency-Key
   - Hash formula: sha256(client_key + ":" + user_id + ":" + booking_id)
   - L1 (Redis): idempotency:payment:{hash}, TTL 24h
   - L2 (Postgres): payment_obligations.idempotency_key (VARCHAR 255, UNIQUE)

✅ Webhook Receiver:
   - POST /webhook/payment dengan payload: external_transaction_id, status, 
     amount, signature (body)
   - Signature source (defensive, per FLAG #6): header X-Gateway-Signature 
     PRIMARY, fallback ke body.signature
   - Signature validation (HMAC-SHA256, key dari env 
     PAYMENT_GATEWAY_WEBHOOK_SECRET)
   - Non-final status handling (FLAG #7): PENDING/CHALLENGE → ACK 200 tanpa mutate DB
   - Final status SUCCESS → UPDATE payment_obligations SET status = 'PAID'
   - Trigger check_booking_payment_complete → tickets generated

✅ Booking Expiry Worker (BookingExpiryWorker):
   - CONSUMER ONLY — message `release_seat_check` sudah di-emit oleh FASE 3
     saat booking dibuat (via LockSeats service). FASE 4 TIDAK emit ulang.
   - T+3min lazy-check: cek booking.payment_status
   - If PAID → no-op
   - If PENDING → rollback: release Redis bits, set booking EXPIRED, 
     set obligations EXPIRED, refund paid obligations
   - Refund retry: 3 attempts + log REFUND_FAILED ke admin_actions (FLAG #4)

✅ Webhook Reconciliation Worker:
   - Berjalan setiap 10 menit
   - Cari payment_obligations dengan status='PENDING' AND created_at > 10min
   - Panggil Payment Gateway API GET /transactions/{external_transaction_id}
   - Update status sesuai respons Gateway
   - Log ke admin_actions

✅ Bulk Ticket Assignment (POST /payments/bulk/assign):
   - Leader assigns tickets to members
   - Validate: leader_user_id == JWT sub
   - Validate: target user status='ACTIVE' (not suspended/frozen/deleted)
   - Validate: event.event_start_time > NOW() (FLAG #7 — event belum mulai)
   - Atomic: all-or-nothing (rollback if any fails)
   - Update tickets SET owner_user_id, is_assigned = TRUE
   - RowsAffected check untuk detect silent failure

✅ Database Trigger:
   - check_booking_payment_complete: AFTER UPDATE ON payment_obligations
   - If all obligations PAID → booking PAID + generate tickets
   - BULK mode: 1 ticket per seat, seat list dari bookings.seat_positions 
                (JSONB array), owner = leader_user_id, is_assigned = FALSE
   - SPLIT mode: 1 ticket per obligation, seat dari payment_obligations.
                 seat_position, owner = obligation.user_id, is_assigned = TRUE
   - Defensive check: seat_position NOT NULL for SPLIT mode (RAISE EXCEPTION)

3.1 FROM PRD v6.0 §F003 — SPLIT-PAY EXECUTION ENGINE SPEC
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION:
  Mengelola pembayaran terpisah untuk grup secara event-driven dengan 
  mekanisme fallback otomatis jika batas waktu 3 menit habis.

INPUTS:
  - Booking Reference ID, Array of User IDs, Amount per user, Payment Method, 
    Payment Mode (SPLIT | BULK)

PROCESS — SPLIT Mode:
  1. Buat Payment Obligation per user (status PENDING, TTL 3 menit)
  2. Kirim payment link ke setiap anggota
  3. Setiap anggota bayar sendiri

PROCESS — BULK Mode:
  1. Leader bayar total seluruh tiket
  2. Booking langsung CONFIRMED tanpa menunggu anggota lain
  3. Tiket dimiliki Leader, bisa di-assign ke anggota

PROCESS — Event-Driven:
  - Webhook SUCCESS → update PAID → check all PAID → CONFIRMED
  - Webhook FAILED/TIMEOUT → delayed msg T+3min → Lazy-Check
  - Webhook Reconciliation Worker → poll Gateway every 10min

EDGE CASES:
  - Partial payment → rollback + auto refund
  - Double payment → idempotency key mencegah
  - Webhook timeout → retry 3x + fallback reconciliation
  - Bulk + Assign → sebelum acara

────────────────────────────────────────────────────────────────────────────────

ENUMs (relevan):

  payment_mode_enum   : SPLIT | BULK
  payment_method_enum : VA | E_WALLET | CREDIT_CARD

                        RESALE_PENDING | RESOLD | CANCELLED | USED

PAYMENT_OBLIGATIONS TABLE:
  - id, booking_id (FK), user_id (FK), seat_position (nullable)
  - amount NUMERIC(15,2) > 0
  - status payment_status_enum DEFAULT 'PENDING'
  - payment_method (nullable)
  - payment_link VARCHAR(255) UNIQUE
  - external_transaction_id VARCHAR(255)
  - webhook_received_at TIMESTAMPTZ
  - idempotency_key VARCHAR(255) UNIQUE
  - refunded_at, refund_transaction_id
  - created_at, updated_at

TICKETS TABLE (untuk trigger):
  - id, booking_id, payment_obligation_id (nullable), owner_user_id
  - section_id, seat_position, status, is_assigned
  - qr_secret_key, fallback_pin (UNIQUE)
  - fallback_pin_used_at, fallback_pin_used
  - original_owner_user_id (nullable), resale_transaction_id (nullable)
  - created_at, updated_at

TRIGGER check_booking_payment_complete:
  Fires WHEN NEW.status = 'PAID'. Flow:
    1. SELECT booking FOR UPDATE
    2. If booking.payment_status = 'PENDING':
       a. Check IF NOT EXISTS obligation WHERE status != 'PAID'
       b. If all PAID:
          - UPDATE bookings SET payment_status = 'PAID'
          - BULK: SOURCE = bookings.seat_positions (JSONB) — BUKAN 
                  payment_obligations.seat_position (NULL di BULK)
                  owner = leader_user_id, is_assigned = FALSE
          - SPLIT: SOURCE = payment_obligations.seat_position (1 per obligation)
                   RAISE EXCEPTION if NULL, owner = obligation.user_id, 
                   is_assigned = TRUE

CATATAN KRITIS: Di BULK mode, payment_obligations.seat_position = NULL. 
Trigger WAJIB baca daftar kursi dari bookings.seat_positions.

RLS POLICIES (payment_obligations):
  - Users view own obligations → SELECT if user_id = auth.uid()
  - Users update own obligations → UPDATE if user_id = auth.uid() 
                                    AND status = 'PENDING'
  - Admins view all obligations → SELECT if role IN ('admin', 'event_organizer')

3.3 FROM LOGIC_FLOW v1.4 §4 — FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

SPLIT MODE SEQUENCE:

  Step 1: CREATE PAYMENT OBLIGATIONS
    FOR EACH user IN group:
      - Call Payment Gateway initiate charge
      - INSERT payment_obligations (with idempotency_key hash, status PENDING)

  Step 2: SEND NOTIFICATIONS (async — FCM/Email/SMS)

  Step 3: WAIT FOR WEBHOOK (event-driven)
    [CASE A: SUCCESS]
      - Validate signature + idempotency
      - UPDATE obligation status = 'PAID'
      - Trigger fires → tickets generated if all PAID
    [CASE B: FAILED/TIMEOUT]
      - Retry 3x exponential backoff
      - If still fail → status = 'FAILED'

  Step 4: DELAYED MESSAGE WORKER (BookingExpiryWorker)
    - Consume message at T+3min (emitted by FASE 3)
    - LAZY CHECK:
      IF booking.payment_status = 'PAID': no-op
      ELSIF PENDING/EXPIRED:
        Rollback:
          1. FOR UPDATE booking
          2. Release seats: FOR EACH seat_pos → bit_index = seat_pos - 1
                            SETBIT(key, bit_index, 0)
          3. UPDATE bookings SET payment_status = 'EXPIRED'
          4. UPDATE obligations SET status = 'EXPIRED' WHERE status = 'PENDING'
          5. Refund paid obligations (retry 3x, fallback log REFUND_FAILED)
          6. INSERT admin_actions (FORCE_RELEASE_SEAT)
          7. Notify anggota

BULK MODE SEQUENCE:

  Step 1: CREATE SINGLE OBLIGATION
    - INSERT payment_obligations (seat_position = NULL, amount = total)

  Step 2: WAIT FOR WEBHOOK
    - Trigger: SOURCE = bookings.seat_positions
    - Generate 1 ticket per seat, owner = leader, is_assigned = FALSE

  Step 3: ASSIGN TICKET (Leader → Members) — opsional
    - POST /payments/bulk/assign
    - Validate event not started (FLAG #7)
    - UPDATE tickets SET owner, is_assigned = TRUE

WEBHOOK RECONCILIATION WORKER:
  Every 10 minutes:
    - SELECT PENDING obligations > 10min old (LIMIT 100)
    - Call Gateway API GET /transactions/{txid}
    - IF PAID → UPDATE status + log admin_actions (MANUAL_PAID)
    - IF PENDING → skip
    - ELSE → UPDATE status = FAILED + rollback

IDEMPOTENCY PATTERN (L1 + L2):

  Step 1: Compute hash = sha256(client_key + ":" + user_id + ":" + booking_id)
  Step 2: L1 Redis GET idempotency:payment:{hash}
          - IF found → return cached
  Step 3: L2 Postgres SELECT WHERE idempotency_key = {hash}
          - IF found → return cached (from DB)
          - ELSE → process: Gateway init → INSERT → cache L1 → return

3.5 FROM TDD v1.10 §6.3 — IMPLEMENTATION FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

PAYMENT INITIATION — Flow:

  Function InitiatePayments(ctx, req):
    Step 1: BEGIN transaction
    Step 2: SELECT booking FOR UPDATE WHERE payment_status='PENDING'
    Step 3: Verify leader_user_id == JWT sub
    Step 4: FOR EACH member:
      a. Gateway.InitiatePayment → { TransactionID, PaymentLink }
      b. Compute idempotency hash
      c. INSERT payment_obligations
    Step 5: COMMIT
    Step 6: Return obligations + expires_at

  NOTE (FLAG #7): Delayed message `release_seat_check` sudah di-emit 
  oleh FASE 3 (LockSeats service) saat booking dibuat. FASE 4 TIDAK 
  emit ulang. FASE 4 hanya consume di BookingExpiryWorker.

WEBHOOK HANDLER — Flow (FLAG #6 + #7):

  Function HandleWebhook(ctx, payload):
    Step 1: Extract signature from DUAL SOURCE:
              a. PRIMARY: header "X-Gateway-Signature"
              b. FALLBACK: payload.signature (body)
              - If neither present → 401
    Step 2: Validate signature (via MidtransPaymentAdapter)
              - HMAC-SHA256 generic OR Midtrans SHA512 formula
              - If invalid → 401
    Step 3: BEGIN transaction
    Step 4: SELECT obligation FOR UPDATE BY external_transaction_id
              - If not found → 404
    Step 5: IF obligation.status = 'PAID' → return 200 (idempotent)
    Step 6: STATUS BRANCHING (FLAG #7):
              - IF payload.Status IN ('PENDING', 'CHALLENGE'):
                  * ACK 200 tanpa memutasi DB
                  * Log info "non-final status received"
                  * Return 200 (prevent Gateway retry storm)
              - IF payload.Status = 'SUCCESS' (final):
                  * UPDATE status = 'PAID', webhook_received_at = NOW()
              - ELSE (final fail: DENY/CANCEL/EXPIRE):
                  * UPDATE status = 'FAILED'
    Step 7: COMMIT — trigger fires automatically
    Step 8: Return 200

BOOKING EXPIRY WORKER — Flow (FLAG #4 + #5):

  Function ProcessReleaseSeatCheck(ctx, msg):
    Step 1: Deserialize { booking_id }
    Step 2: SELECT booking BY id (not found → ACK)
    Step 3: IF payment_status = 'PAID' → no-op
    Step 4: IF payment_status = 'PENDING':
              - executeRollback:
                a. FOR UPDATE booking
                b. Release seats (FLAG #5):
                     FOR EACH seat_pos IN booking.seat_positions (JSONB):
                       bit_index = seat_pos - 1
                       SETBIT(key, bit_index, 0)
                c. UPDATE bookings SET payment_status = 'EXPIRED'
                d. UPDATE obligations SET status = 'EXPIRED' WHERE status = 'PENDING'
                e. FOR EACH obligation WHERE status = 'PAID':
                     Gateway.Refund with retry 3x (100ms, 200ms, 400ms)
                     - If success → UPDATE status = 'REFUNDED'
                     - If all fail → INSERT admin_actions (
                         action_type = 'MANUAL_REFUND',
                         reason = 'REFUND_FAILED_RETRY_EXHAUSTED'
                       ) + log CRITICAL
                f. INSERT admin_actions (FORCE_RELEASE_SEAT)
                g. COMMIT
              - Notify anggota

BULK ASSIGN — Flow (FLAG #7):

  Function BulkAssign(ctx, req):
    Step 1: SELECT booking WHERE id = req.BookingID
              - Verify leader_user_id = current_user (JWT)
              - If not → 403
    Step 2: EVENT TIME VALIDATION (FLAG #7):
              - SELECT e.event_date, e.event_start_time FROM events e
                JOIN bookings b ON b.event_id = e.id
                WHERE b.id = req.BookingID
              - Combine event_date + event_start_time → event_start_at
              - IF event_start_at <= NOW():
                  RETURN 422 EVENT_ALREADY_STARTED
    Step 3: BEGIN transaction
    Step 4: FOR EACH assignment:
              a. SELECT user status + is_blacklisted
                 - If not found → FAILED, break
              b. IF status != 'ACTIVE' → FAILED (422), break
              c. IF is_blacklisted → FAILED, break
              d. UPDATE tickets SET owner, is_assigned=TRUE
                 WHERE id AND booking_id AND is_assigned=FALSE
              e. RowsAffected == 0 → FAILED, break
    Step 5: IF !allSuccess → ROLLBACK + return 409
    Step 6: COMMIT + return 200

WEBHOOK RECONCILIATION WORKER:
  Every 10 min: SELECT PENDING > 10min (LIMIT 100)
  FOR EACH: Gateway GET /transactions/{txid}
    - PAID → UPDATE + admin_actions MANUAL_PAID
    - PENDING → skip
    - ELSE → UPDATE FAILED + rollback

MIDTRANS PAYMENT ADAPTER:

  Interface PaymentGateway:
    - InitiatePayment(ctx, req) → { TransactionID, PaymentLink }
    - Refund(ctx, transactionID, amount) → { RefundID }
    - Payout(ctx, req) → { PayoutID }
    - ValidateWebhookSignature(headers, payload) → bool

  MidtransPaymentAdapter:
    - Initiate: POST /v2/charge
    - Refund: POST /v2/{order_id}/refund
    - Payout: POST /v2/payout
    - ValidateWebhookSignature:
        Extract: header "X-Gateway-Signature" OR payload["signature"]
        Formula: SHA512(order_id + status_code + gross_amount + ServerKey)
        Constant-time compare

  Auth:     Required (JWT, booking leader)
  Rate:     30 req/min per user
  Headers:  X-Idempotency-Key REQUIRED

  Request: { booking_id, assignments: [{ ticket_id, user_id }] }

  Success (200): { booking_id, assigned, tickets }

  Errors: 
    - 403 (not leader)
    - 409 (partial failure → rollback)
    - 422 (target inactive)
    - 422 EVENT_ALREADY_STARTED (FLAG #7 — event sudah mulai)

ENDPOINT 4 — POST /webhook/payment

  Auth: Signature validation (header OR body)
  Rate: Unlimited (trusted source)

  Request: 
    {
      "external_transaction_id": "txn-gateway-123",
      "status": "SUCCESS",
      "amount": "1000000",
      "signature": "hmac-sha256-of-payload"
    }

  Signature extraction (FLAG #6):
    - Primary: header "X-Gateway-Signature"
    - Fallback: body "signature"

  Status handling (FLAG #7):
    - SUCCESS (final) → UPDATE PAID
    - PENDING / CHALLENGE (transitional) → ACK 200, NO mutate
    - DENY / CANCEL / EXPIRE (final fail) → UPDATE FAILED

  Success (200): { status: "processed" } atau { status: "acknowledged" }

  Errors: 401 (invalid signature), 404 (transaction not found)

8.7 WEBHOOK NON-FINAL STATUS (FLAG #7 DETAIL)
────────────────────────────────────────────────────────────────────────────────

  Rationale:
    - Prevent Gateway retry storm (Midtrans akan retry jika kita return non-200)
    - Preserve state untuk status final
    - Reconciliation worker akan resolve nanti jika stuck di PENDING

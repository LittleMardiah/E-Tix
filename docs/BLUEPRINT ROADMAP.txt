1. TUJUAN & FILOSOFI BLUEPRINT
================================================================================

TUJUAN BLUEPRINT ROADMAP.txt
────────────────────────────────────────────────────────────────────────────────

Blueprint ini menjawab SATU pertanyaan fundamental:

  ❓ "Berapa banyak ROADMAP FASE (...) file yang perlu dibuat untuk 
      mengeksekusi E-Tix Flash dari nol sampai Live Demo?"

Dan memberikan jawaban definitif + justifikasi yang bisa diaudit:

  ✅ "10 file — FASE 0 sampai FASE 9, dengan struktur, scope, dan 
      urutan yang sudah terkunci di blueprint ini."

FILOSOFI
────────────────────────────────────────────────────────────────────────────────

Blueprint ini lahir dari masalah nyata: 

  📖 "Setiap kali masuk eksekusi, kita dipaksa bolak-balik baca 9 dokumen 
      fondasi (PRD, DB Schema, Logic Flow, HALAMAN, TDD, API Contract, 
      Security Spec, DRP, STP) hanya untuk tahu 'apa yang harus dilakukan 
      minggu ini'. Itu tidak sustainable."

Solusi:

  🎯 Setiap ROADMAP FASE (...) file WAJIB SELF-CONTAINED — distilasi 
      dari 9 dokumen fondasi, sehingga eksekutor HANYA butuh file fase itu 
      untuk bekerja. Tidak perlu baca ulang fondasi.

  🎯 Blueprint ini adalah PETA-nya. Tanpa blueprint, kita bisa bikin 
      fase yang overlap, gap, atau drift.

2. PROBLEM STATEMENT YANG DIPECAHKAN
================================================================================

MASALAH 1: Fragmentasi Eksekusi
  Tanpa blueprint, kita akan bikin fase berdasarkan insting — bisa 5 fase, 
  bisa 15 fase, tidak ada baseline. Hasilnya: tidak konsisten, tidak bisa 
  diukur, tidak bisa di-review.

MASALAH 2: Cognitive Overload
  Setiap eksekusi harus baca 9 dokumen (PRD, DB, LOGIC, HALAMAN, TDD, API, 
  SECURITY, DRP, STP). Total ~200 halaman. Tidak efisien.

MASALAH 3: Traceability Gap
  Tidak ada matriks yang menghubungkan "task X di fase Y" dengan "requirement 
  Z di PRD" — sehingga sulit audit kelengkapan.

MASALAH 4: Drift Risk
  Tanpa guardrail, fase bisa nambah fitur, ubah scope, atau lupa requirement. 
  Bahaya bagi konsistensi portfolio.

SOLUSI BLUEPRINT:
  ✅ Definisikan jumlah fase secara definitif (10 file).
  ✅ Setiap fase distilasi jadi self-contained file.
  ✅ Traceability matrix (Foundation → FASE) disediakan.
  ✅ Anti-drift guardrails eksplisit.

3. PRINSIP PENYUSUNAN ROADMAP FASE
================================================================================

PRINSIP 1 — FEATURE-DRIVEN GRANULARITY
  Setiap fase harus map ke 1 fitur utama (F00X) ATAU 1 prerequisite 
  kelompok kerja (setup, auth, testing). Tidak boleh ada fase "campur aduk".

PRINSIP 2 — SELF-CONTAINED OUTPUT
  Setiap ROADMAP FASE file WAJIB memuat:
    - Scope fitur (dari PRD)
    - Tabel & ENUM yang relevan (dari DATABASE_SCHEMA)
    - State machine & sequence flow (dari LOGIC_FLOW)
    - Wireframe screens yang relevan (dari HALAMAN)
    - Technical implementation notes (dari TDD — snippet, config)
    - Endpoints (dari API_CONTRACT)
    - Security requirements (dari SECURITY_SPEC)
    - Playbook terkait (dari DRP)
    - Test cases (dari STP)
  Tujuannya: eksekutor TIDAK PERLU buka 9 dokumen fondasi lagi.

PRINSIP 3 — DEPENDENCY-AWARE ORDERING
  Urutan fase mengikuti dependency graph (PRD §Feature Dependency):
    F001 (None) → F002 (F001) → F003 (F002) → F004 (F003) → F004b (F004) 
    → F005 (F003, F004) → F006 (F001-F005)

PRINSIP 4 — VERIFIABLE DELIVERABLE
  Setiap fase punya:
    - Deliverable (apa yang jadi)
    - Acceptance criteria (dari STP)
    - Definition of Done (DoD)
    - Rollback point (kalau gagal)

PRINSIP 5 — INCREMENTAL VALUE
  Setiap fase menghasilkan sesuatu yang bisa didemokan secara parsial 
  (meski belum full-system). Contoh: setelah FASE 3 (F002), kita sudah 
  bisa demo "seat locking" meski belum ada payment.

4. ATURAN EMAS (GOLDEN RULES) — WAJIB DIPATUHI
================================================================================

🚫 RULE 1 — NO SPECIFICATION DRIFT
   ROADMAP FASE dilarang menambah fitur, tabel, endpoint, ENUM, atau 
   kolom baru yang tidak ada di 9 dokumen fondasi.

🚫 RULE 2 — NO WALLET / LEDGER
   E-Tix Flash TIDAK punya internal wallet/ledger (PRD §Out of Scope).
   Semua transaksi keuangan via Payment Gateway. Tidak ada "ledger_entries", 
   "wallets", "balance_after", dst.

🚫 RULE 3 — NO GHOST ENDPOINTS
   Endpoint yang ada di ROADMAP FASE harus 1:1 dengan API_CONTRACT v1.2.
   Dilarang ada /auth/change-password, /auth/forgot-password, dll (out of scope).

🚫 RULE 4 — NO GHOST COLUMNS
   Kolom yang direferensikan harus ada di DATABASE_SCHEMA v2.9. Tidak boleh 
   refer `users.bank_account_number`, `users.national_id`, `bookings.is_settled`.

🚫 RULE 5 — NO GHOST ERROR CODES
   Error code yang dipakai harus 1:1 dengan API_CONTRACT §3.2. Contoh: 
   `INVALID_QR_OR_TICKET_MISMATCH` (bukan `EXPIRED_QR`), 
   `UNPROCESSABLE_ENTITY` (bukan `PAYLOAD_TOO_LARGE` untuk business rule).

🚫 RULE 6 — NO DUPLIKASI CONTENT
   Kalau suatu konten sudah ada di foundation, ROADMAP FASE memuat DISTILASI 
   (bukan copy-paste full). Kalau ada runbook panjang, cukup refer + ringkas.

🚫 RULE 7 — NO TIME-ABSOLUTE COMMITMENT
   Gunakan "Week 1", "Week 2" (relatif), bukan tanggal absolut seperti 
   "2026-09-15". Portfolio project, fleksibel.

🚫 RULE 8 — SINGLE SOURCE OF TRUTH
   Kalau ada konflik antar fondasi, TRUTH FROM FOUNDATION berlaku: 
   PRD > DATABASE_SCHEMA > LOGIC_FLOW > HALAMAN > TDD > API_CONTRACT > 
   SECURITY_SPEC > DRP > STP.

   - Portfolio value berkurang (kelihatan tidak fokus)

10. ANTI-DRIFT GUARDRAILS
================================================================================

G1 — TRACEABILITY ENFORCEMENT
  Setiap ROADMAP FASE file WAJIB mencantumkan "Cross-Reference Foundation" 
  di header, dan setiap task harus trace ke minimal 1 section di foundation.

G2 — SCOPE FREEZE
  Scope fase tidak boleh bertambah setelah blueprint di-approve. Kalau ada 
  kebutuhan baru, harus revisi blueprint (dengan approval User).

G3 — NO WALLET/LEDGER
  Semua fase finansial (FASE 4, 7, 8) WAJIB compliance dengan PRD §Out of Scope:
  semua via Payment Gateway, tanpa internal wallet/ledger.

G4 — ENUM CONSISTENCY
  Semua status/enum yang dipakai di fase harus match DATABASE_SCHEMA v2.9:
  - ticket_status_enum: CONFIRMED (bukan ISSUED)
  - scan_status_enum: ALREADY_USED (bukan DUPLICATE_SCAN_REJECTED)
  - dst.

G5 — ERROR CODE CONSISTENCY
  Semua error code harus 1:1 dengan API_CONTRACT v1.2 §3.2:
  - INVALID_QR_OR_TICKET_MISMATCH (bukan EXPIRED_QR)
  - UNPROCESSABLE_ENTITY (bukan PAYLOAD_TOO_LARGE untuk business rule)
  - 413 Payload Too Large (HTTP standard, bukan custom)

G6 — HEADER CONSISTENCY
  - X-Idempotency-Key: untuk semua POST mutations
  - X-Queue-Token: untuk seat locking (FASE 3)
  - X-Admin-2FA-Token: untuk admin financial (FASE 8)

G7 — SELF-CONTAINED FILE
  Setiap ROADMAP FASE file WAJIB bisa dibaca standalone tanpa refer balik ke 
  fondasi. Kalau butuh snippet panjang (Lua, SQL, Go), copy ke file fase itu.

G8 — ACCEPTANCE CRITERIA BINDING
  Setiap fase WAJIB punya AC yang jelas. Kalau tidak terpenuhi → fase tidak 
  boleh di-mark "Done".

    ROADMAP FASE (0).txt

  Mulai dari FASE 0. Eksekutor HANYA baca ROADMAP FASE (0).txt, 
  tidak perlu balik ke fondasi.

LANGKAH 6 — PROGRESS TRACKING
  Setiap selesai fase, update status di ROADMAP FASE file: 
  Not Started → In Progress → Done.

## 📋 EXECUTIVE SUMMARY

**Problem Statement**
Sistem tiket konser dan acara besar saat ini kerap mengalami server crash akibat high concurrency serta dikuasai oleh scalper bot (calo) yang memborong ribuan tiket dalam hitungan detik. Selain itu, pembelian tiket kelompok sering gagal karena ketiadaan mekanisme atomic locking untuk banyak kursi sekaligus.

**Solution Overview**
E-Tix Flash adalah platform pemesanan tiket berbasis Golang yang menggunakan Behavioral Ingress Engine untuk menyaring bot, In-Memory Bitmask Group Locking untuk pemesanan denah kursi berdampingan secara atomic, serta Controlled Resale Market dengan price-cap resmi.

**Value Proposition**
Berbeda dari sistem FCFS (First-Come, First-Served) standar, E-Tix Flash menjamin alokasi tiket yang adil bagi manusia asli (anti-bot), mencegah penjualan calo di pihak ketiga lewat Dynamic HMAC QR, serta memberikan fleksibilitas bayar terpisah (split-pay) untuk grup.

**Target Users**
- **Event Organizer (EO) / Promotor**: Pihak yang ingin menjual tiket tanpa gangguan bot dan menjaga reputasi acara.
- **End Customer / Fans**: Pembeli tiket individu maupun kelompok yang membutuhkan akses antrean adil dan pemesanan kursi berdampingan.

## 🎯 OBJECTIVES & SUCCESS CRITERIA

### Primary Objectives
- Menahan dan memfilter lonjakan trafik (peak traffic) hingga puluhan ribu requests per second (RPS) tanpa membuat basis data utama tumbang.
- Memblokir minimal 95% scalper bot sebelum menyentuh transactional engine.
- Menyediakan mekanisme penguncian kursi grup secara atomic (N-kursi sekaligus) dengan latensi pemrosesan di bawah 50 milidetik.
- Memberikan nilai tambah bisnis pasca-acara melalui analytics dan insight untuk EO.
- Membangun sistem yang maintainable dan siap dievolusi untuk skala lebih besar.

| API Latency (p95) | < 100 ms | Terukur via Prometheus & Grafana saat beban puncak |

| Group Lock Success Rate | 100% (No Race Condition) | Tidak ada double-booking pada kursi yang sama |
| System Uptime | 99.9% | Terpantau selama periode flash sale berlangsung |
| Post-Event Report Generation | < 1 hour after event ends | Terukur dari waktu event selesai hingga report tersedia |

## 📐 FUNCTIONAL REQUIREMENTS (Detailed)

### Requirement F001: Behavioral Ingress & Fan-Score Queueing (with Priority Tier)
**Description:** Menangani ingress traffic saat flash sale dengan memisahkan beban kerja menjadi dua tahap (synchronous cepat dan asynchronous mendalam) untuk menjaga latency tetap rendah. Menggunakan pre-computed base score untuk menghindari cold-start pada request pertama pengguna. Memberikan akses prioritas kepada fans loyal.

**Inputs:**
- User ID (UUID string)
- Device Fingerprint (encrypted string)
- Access Metadata (request interval, IP, TLS parameters)

**Process:**

**Pra-Flash Sale (Pre-Computation):**
- Sistem menghitung Base Score untuk setiap user berdasarkan data statis:
  - Umur akun (semakin tua, semakin tinggi skor)
  - Status verifikasi (email + phone terverifikasi memberikan skor tambahan)
  - **Loyalty Score:** Riwayat pembelian tiket sebelumnya
    - Pernah beli 1x → +10 poin
    - Pernah beli 3x → +30 poin
    - Pernah beli 5x+ → +50 poin
- Base Score disimpan di cache dengan TTL hingga acara selesai.

**Stage 1 (Synchronous - Target < 1ms):** Berjalan di API Gateway/Golang Middleware.
- Rate Limiter memeriksa limit akses per IP/User ID.
- Validasi header dasar (User-Agent, Accept-Language).
- Cek blacklist IP yang di-cache di memory.
- Baca Base Score dari cache sebagai nilai awal Fan Score.

**Stage 2 (Asynchronous - Background Worker):** Jika lolos Stage 1, metadata dikirim ke Message Broker.
- Behavioral Scorer Worker menghitung Dynamic Score berdasarkan pola request real-time (interval antar request, pola klik, device fingerprint).
- Dynamic Score digabungkan dengan Base Score untuk menghasilkan Final Fan Score.
- Hasil akhir (Final Fan Score) disimpan di cache dengan TTL yang diperpanjang.

**Priority Tier System (Waiting Room):**
- **Tier 1 (VIP Fans):** Skor > 90 → Priority access (kelompok pertama yang dilayani).
- **Tier 2 (Regular Fans):** Skor 70-90 → Access normal.
- **Tier 3 (New Users / Low Score):** Skor < 70 → Access setelah Tier 1 & 2 selesai.
- EO dapat melihat dashboard real-time: "Berapa banyak fans setia yang berhasil membeli tiket?"

**Outputs:**
- Signed Queue Token (JWT dengan payload expiry & priority tier)
- Error Response / HTTP 429 Too Many Requests (jika melampaui rate limit)
- Waiting Room dengan visualisasi tier

**Edge Cases:**
- *Traffic Spike Extreme (>50,000 RPS)* → Ingress mengaktifkan Circuit Breaker dan menahan request di Virtual Waiting Room via WebSocket Cluster.
- *User baru tanpa Base Score* → Gunakan nilai default (skor 50) + pantau perilaku di Stage 2.
- *Cache Cluster Failure* → Sistem masuk ke Degraded Mode (lihat NFR Reliability).
- *Fans setia yang terlambat masuk waiting room* → Tetap mendapat prioritas meskipun datang belakangan (selama masih dalam waktu flash sale).

### Requirement F002: Bitmask Multi-Seat Atomic Locking
**Description:** Mengunci N-kursi berurutan secara atomik dalam denah panggung menggunakan operasi bitwise di memori. Denah kursi dipartisi per section untuk mengurangi konflik, dan mapping kursi dibuat immutable setelah layout diterbitkan.

**Inputs:**
- Event ID (UUID)
- Section ID (string)
- Seat IDs (Array of Integers / Bit Positions)
- User Queue Token (Valid JWT)

**Process:**
1. Engine memuat Bitmask Matrix dari cache berdasarkan Section ID (setiap section adalah key terpisah).
2. Sistem menjalankan operasi bitwise untuk memeriksa ketersediaan N kursi secara simultan dalam satu operasi atomic.
3. Jika seluruh kursi tersedia (bernilai 0), sistem mengubah status kursi menjadi terkunci (bernilai 1) dan menyimpan pemetaan ID Pengguna dengan TTL 180 detik.
4. Sistem mengirim event payload ke Message Broker untuk memicu proses Split-Pay (F003).

**Catatan Kritis - Immutability:**
> Pemetaan Seat ID ↔ Bit Position Offset bersifat immutable setelah section layout diterbitkan. Setiap perubahan layout (penambahan/penghapusan kursi) WAJIB membuat versi layout baru dan tidak boleh mengubah mapping yang sudah ada. Hal ini untuk menjaga integritas operasi bitwise di tengah acara berlangsung.

**Outputs:**
- Booking Reference ID
- Seat Allocation Map (JSON response)
- Expiry Timestamp (Epoch ISO8601)

**Edge Cases:**
- *Partial Seat Lock Conflict* (1 dari 4 kursi tiba-tiba diambil pengguna lain) → Sistem langsung membatalkan lock untuk seluruh N kursi (Rollback All) dan mengembalikan pesan "Seats No Longer Available".
- *Cache Cluster Failure* → Sistem masuk ke Degraded Mode (lihat NFR Reliability).

### Requirement F003: Group Split-Pay Execution Engine (Hybrid Mode)
**Description:** Mengelola pembayaran terpisah untuk grup secara event-driven dengan mekanisme fallback otomatis jika batas waktu 3 menit habis. Menyediakan dua mode pembayaran untuk fleksibilitas pengguna.

**Inputs:**
- Booking Reference ID
- Array of User IDs (pembeli dalam grup)
- Amount per user (decimal)
- Payment Method (VA, E-Wallet, Kartu Kredit)
- Payment Mode: `SPLIT` atau `BULK`

**Process:**

**Mode 1: Split-Pay (Individual)**
1. Sistem membuat Payment Obligation per user dan menyimpan status di cache dengan TTL 3 menit.
2. Sistem mengirim link pembayaran unik ke setiap anggota grup (via push notifikasi / email / SMS).
3. Setiap anggota membayar bagiannya sendiri melalui link yang diterima.

**Mode 2: Bulk Payment (Leader Pays All)**
1. Satu anggota (pemimpin grup) membayar total seluruh tiket sekaligus.
2. Sistem langsung mengubah status booking menjadi CONFIRMED tanpa menunggu anggota lain.
3. Tiket tetap dikirim ke seluruh anggota grup, namun kepemilikan awal berada di tangan Leader.

**Aturan Kepemilikan Tiket untuk Bulk Mode:**
- Secara default, tiket dimiliki oleh Leader (pembayar).
- Leader memiliki opsi untuk **"Assign Ticket"** ke anggota grup melalui dashboard.
- Setelah di-assign, tiket menjadi milik anggota tersebut dan anggota dapat mengelola tiketnya sendiri (termasuk menjual via F005).

**Event-Driven Monitoring (Tanpa Polling untuk Kedua Mode):**

**Skenario Sukses (Split Mode):**
- Payment Gateway mengirim Webhook ke sistem.
- Sistem menerima webhook, meng-update status user menjadi PAID.
- Sistem mengecek apakah semua anggota sudah lunas. Jika iya, status booking berubah menjadi CONFIRMED dan kursi final.
- Webhook bersifat idempotent; jika webhook duplikat datang, sistem mengabaikannya.

**Skenario Gagal/Timeout (Idempotent Lazy-Check Pattern):**
- Saat lock pertama kali dibuat, sistem mengirim pesan ke Message Broker dengan delay tepat 3 menit (pesan ini tidak pernah dibatalkan).
- Ketika pesan sampai di T+3 menit, worker melakukan lazy check:
  - Cek status booking di cache/database.
  - Jika status sudah CONFIRMED → worker mengabaikan pesan (no-op).
  - Jika status masih PENDING_SPLIT_PAY → worker menjalankan rollback atomik (melepas semua kursi grup), mengirim notifikasi ke semua anggota, dan menginisiasi refund otomatis ke user yang sudah bayar.

**Webhook Reconciliation Worker (Fallback untuk Webhook Hilang):**
- Worker berjalan setiap 10 menit untuk memeriksa transaksi dengan status PENDING yang sudah melewati TTL 3 menit.
- Worker menghubungi Payment Gateway via API untuk mengecek status pembayaran secara langsung.
- Jika Payment Gateway menyatakan SUDAH BAYAR, worker meng-update status menjadi PAID dan membatalkan refund (jika belum dieksekusi).
- Jika Payment Gateway menyatakan BELUM BAYAR, worker menganggap rollback sudah benar.

**Outputs:**
- Payment Status per user (PENDING / PAID / EXPIRED)
- Final Confirmation (Booking ID, QR Code payload, Static Fallback PIN)

**Edge Cases:**
- *Partial payment (1 dari 4 bayar)* → Saat TTL habis, semua kursi di-rollback, dan sistem menginisiasi refund otomatis ke user yang sudah bayar (via idempotency key).
- *Double payment* → Idempotency key mencegah duplikasi transaksi.
- *Webhook timeout* → Sistem melakukan retry dengan exponential backoff (3x), jika gagal → Webhook Reconciliation Worker mengambil alih.
- *Bulk Mode + Assign Ticket* → Leader dapat mengalihkan kepemilikan tiket ke anggota grup kapan saja sebelum acara dimulai.

### Requirement F004: Dynamic HMAC QR + Offline Fallback PIN
**Description:** Membuat kode QR dinamis yang selalu berubah setiap 30 detik untuk mencegah pencurian atau penggandaan tiket fisik/tangkapan layar. Menyediakan Static Fallback PIN untuk situasi darurat (HP mati, sinyal buruk).

**Inputs:**
- Ticket ID (UUID)
- Current Owner User ID (UUID)
- Secret System Key (Secure Environment Variable)

**Process:**

**Primary Method: Dynamic HMAC QR**
1. Sistem memuat stempel waktu (timestamp) server terbaru (dalam blok 30 detik).
2. Sistem menghitung HMAC-SHA256 dari gabungan `TicketID + OwnerID + Timestamp Block`.
3. Sistem menampilkan string terenkripsi pada antarmuka aplikasi pembeli sebagai kode QR.
4. QR Code berganti setiap 30 detik. Screenshot/foto tidak valid karena timestamp akan kedaluwarsa.

**Secondary Method: Static Fallback PIN (Situasi Darurat)**
1. Saat transaksi CONFIRMED, sistem juga mengirimkan **Static Fallback PIN** (12 digit alfanumerik) via SMS dan Email ke setiap pemegang tiket.
2. PIN ini valid **sepanjang hari acara** dan hanya bisa digunakan **1 kali**.
3. PIN dikirim terpisah dari QR Code dan tidak bergantung pada koneksi internet.
4. Petugas gate dapat memasukkan PIN secara manual di aplikasi scanner offline jika QR Code tidak dapat di-scan (HP mati, layar pecah, sinyal hilang).
5. Setelah PIN digunakan, sistem langsung menandainya sebagai `USED` dan tidak bisa dipakai lagi.

**Outputs:**
- Rendered QR Code Image / Encrypted String Payload
- Static Fallback PIN (12-digit alfanumerik) via SMS/Email

**Edge Cases:**
- *Offline Event Gate Validation* → Aplikasi pemindai gatekeeper menyimpan public key untuk verifikasi signature secara lokal tanpa bergantung pada koneksi internet penuh.
- *HP Mati Total* → Pengguna dapat memberikan PIN ke petugas gate untuk verifikasi manual.
- *PIN Bocor* → Karena PIN hanya 1 kali pakai, kebocoran tidak berbahaya. Pemilik asli tetap bisa masuk dengan Dynamic QR sebagai primary method.

### Requirement F004b: Gate Analytics, Post-Event Intelligence & Feedback Loop
**Description:** Memanfaatkan data scan QR di pintu masuk untuk memberikan insight berharga kepada EO setelah acara selesai. Sistem juga belajar dari data untuk memberikan rekomendasi dan otomatisasi konfigurasi.

**Inputs:**
- Ticket ID (UUID)
- Scan Timestamp (timestamp)
- Gate ID (string)
- Scanner Device ID (UUID)

**Process:**

**A. Data Collection & Post-Event Report**
1. Setiap kali QR Code di-scan di gate, sistem mencatat:
   - Waktu scan (akurat hingga detik).
   - Gate mana (Gate A, B, C).
   - Scanner device ID (untuk tracking petugas).
   - Status scan (VALID / INVALID / EXPIRED / ALREADY_USED).
2. Setelah acara selesai, sistem menghasilkan **Post-Event Report** untuk EO:
   - **Total Attendance:** Berapa tiket yang benar-benar digunakan.
   - **No-Show Rate:** Persentase tiket yang tidak digunakan.
   - **Peak Entry Time:** Jam berapa fans paling ramai datang (untuk planning staffing).
   - **Gate Utilization:** Gate mana yang paling padat (untuk perbaikan layout).
   - **Repeat Customer Rate:** Berapa persen pembeli yang pernah beli tiket sebelumnya (untuk loyalty program).
   - **Scan Attempts Analytics:** Berapa banyak percobaan scan invalid (indikasi percobaan fraud).
3. EO dapat mengakses dashboard dan mengekspor report sebagai CSV/Excel.

**B. Feedback Loop & Auto-Configuration (Learning System)**
1. **Gate Optimization:** Dari data gate utilization historis, sistem merekomendasikan jumlah petugas per gate untuk event berikutnya.
2. **Bot Pattern Learning:** Sistem mendeteksi pola IP/device fingerprint yang sering muncul di percobaan invalid dan otomatis mem-blacklist-nya (dengan notifikasi ke admin).
3. **Ticket Pricing Insight:** Dari data no-show rate dan resale activity, sistem memberikan rekomendasi harga untuk event berikutnya.
4. **Staffing Recommendation:** Dari data peak entry time, sistem merekomendasikan jam shift petugas yang optimal.

**Outputs:**
- Post-Event Dashboard (real-time selama acara berlangsung).
- Post-Event Report (PDF/CSV/Excel) dalam 1 jam setelah acara selesai.
- Insight Recommendations untuk event berikutnya.
- Auto-blacklist IP/device yang mencurigakan.

**Edge Cases:**
- *Multiple scan attempts (sama tiket)* → Sistem mencatat setiap percobaan (valid atau invalid) untuk mendeteksi percobaan fraud.
- *Offline scan* → Data tetap tersimpan di scanner offline dan disinkronisasi saat online.
- *No internet di venue* → Scanner tetap bekerja offline, data disinkronisasi saat koneksi pulih.
- *Belum cukup data historis* → Rekomendasi menggunakan rule-based default (misal: 2 petugas per gate).

### Requirement F005: Controlled Secondary Resale Market
**Description:** Memungkinkan pemegang tiket menjual kembali tiketnya di platform resmi dengan price-cap, menggunakan payment gateway sebagai mediator transaksi untuk menghindari kompleksitas internal wallet/ledger.

**Inputs:**
- Ticket ID (UUID)
- Seller User ID (UUID)
- Resale Price (decimal, max +10% face value)
- Buyer User ID (UUID)

**Process:**
1. Sistem memvalidasi tiket masih aktif dan belum dipindahtangankan.
2. Sistem mengunci tiket sementara (status RESALE_PENDING) untuk mencegah double-selling.
3. **Pembayaran via Payment Gateway:** Buyer melakukan pembayaran sebesar harga resale ke platform melalui payment gateway (VA / E-Wallet / Kartu Kredit).
4. **Payout ke Seller:** Platform menerima konfirmasi pembayaran dari payment gateway, kemudian mengirimkan dana ke seller melalui payout API dari payment gateway yang sama.
5. **Transfer Ownership:** Sistem menginvalidasi QR code lama, generate QR code baru untuk buyer, dan mengupdate kepemilikan tiket di database.
6. **Pencatatan Transaksi:** Sistem mencatat riwayat transaksi resale untuk kepentingan audit.

**Aturan Kepemilikan untuk Resale:**
- Hanya pemilik tiket (yang namanya terdaftar di sistem) yang dapat menjual.
- Untuk tiket hasil Bulk Mode yang sudah di-assign ke anggota, anggota tersebut adalah pemilik sah.
- Untuk tiket Bulk Mode yang belum di-assign, hanya Leader yang dapat menjual.

**Outputs:**
- New Ticket Ownership Record
- Resale Transaction Receipt
- Updated QR Code for Buyer

**Edge Cases:**
- *Seller membatalkan resale sebelum buyer bayar* → Sistem melepas lock, status kembali ACTIVE.
- *Buyer gagal bayar* → Sistem melepas lock (tidak ada refund karena belum ada dana masuk).
- *Resale price melebihi cap (+10%)* → Sistem menolak transaksi (HTTP 422).
- *Payout API gagal* → Sistem melakukan retry dengan exponential backoff (3x), jika gagal → status transaksi PENDING_PAYOUT dan admin melakukan manual reconciliation via F006.

### Requirement F006: Admin Emergency & Reconciliation Tools
**Description:** Menyediakan tools bagi admin (EO) untuk menangani situasi darurat dan memastikan sistem tetap terkendali.

**Inputs:**
- Admin User ID (UUID) dengan role khusus
- Event ID (UUID)
- Action Type (string)

**Process:**

**A. Bulk Cancellation & Refund (Emergency Price Error)**
1. Admin mengakses Emergency Dashboard dan memilih event.
2. Admin mengklik "Cancel All Tickets" dan mengisi alasan.
3. Sistem menampilkan konfirmasi: "Anda akan membatalkan X tiket dan refund total Rp Y. Lanjutkan?"
4. Setelah konfirmasi, sistem menjalankan:
   - Mengubah status semua tiket menjadi CANCELLED.
   - Mengirim refund request ke Payment Gateway untuk setiap transaksi.
   - Mengirim notifikasi ke semua pembeli: "Maaf, terjadi kesalahan. Tiket Anda akan di-refund. Mohon maaf."
   - Mengembalikan semua kursi ke pool (bitmask direset ke 0).
5. Semua aksi dicatat di tabel `admin_actions` dengan timestamp, admin ID, dan alasan.

**B. Manual Reconciliation (Payout Gagal / Webhook Hilang)**
1. Admin melihat daftar transaksi dengan status PENDING_PAYOUT atau CONFIRMED yang mencurigakan.
2. Admin dapat memverifikasi status pembayaran melalui Payment Gateway dashboard.
3. Admin dapat:
   - Memaksa update status menjadi PAID (jika sudah bayar tapi webhook hilang).
   - Memaksa refund (jika terjadi kesalahan double charge).
   - Mencatat catatan manual untuk audit.

**C. System Health Monitoring (Read-only)**
1. Admin dapat melihat dashboard real-time:
   - Jumlah request per detik.
   - Cache Cluster health (Redis status).
   - Antrean Message Broker.
   - Error rate dan latency.

**Outputs:**
- Bulk Cancellation Confirmation
- Refund Status Report
- Audit Log Entry

**Edge Cases:**
- *Bulk cancellation dilakukan di tengah flash sale* → Sistem harus tetap responsif. Proses refund dilakukan secara asynchronous (background worker).
- *Refund API gagal* → Retry dengan exponential backoff, jika gagal → status PENDING_REFUND dan admin melakukan manual reconciliation.

### Performance

### Cost Efficiency & Infrastructure Optimization
| Komponen | Estimasi Biaya/Bulan | Catatan |
|----------|---------------------|---------|
| **Golang Backend (Render.com)** | $0 (Free Tier) - $50 (Standard) | Stateless, bisa scale otomatis. Free tier cukup untuk MVP. |
| **PostgreSQL (Supabase)** | $25 (Free tier) - $100 (Pro) | Free tier cukup untuk 10.000 tiket. |
| **Redis Cluster (Upstash)** | $50 (Free tier) - $150 (Pro) | Bitmask Locking & Rate Limiting. |

| **Total** | **~$50 - $350 / bulan** | **Dapat menangani 1-5 event besar per bulan.** |

**Cost-Per-Ticket Metric:**
- **Target:** < Rp 500 per tiket (infra cost).
- **Dengan fee 2.5% dari harga tiket Rp 1.000.000 → Rp 25.000 per tiket.**
- **Profit margin:** Rp 24.500 per tiket (98% margin).

**Mengapa Golang?**
- Memory footprint kecil (~50 MB idle).
- CPU efficient untuk high concurrency (goroutine).
- Mengurangi kebutuhan server mahal.

**Mengapa Redis Bitmask, Bukan PostgreSQL?**
- PostgreSQL Row Lock: 20.000 RPS → butuh 4x server.
- Redis Bitmask: 20.000 RPS → cukup 1 server (single-threaded).
- **Penghematan biaya:** ~70% lebih murah.

### Security
- **Authentication:** OAuth2 dengan JWT Token bertanda tangan.
- **Authorization:** Role-Based Access Control (RBAC: Admin, EO, Customer, Gatekeeper).
- **Data Protection:** Enkripsi database untuk data sensitif, wajib HTTPS/TLS 1.3, hashing PIN/Password.
- **Input Validation:** Strict Whitelist Input Validation pada semua endpoints.
- **Admin Actions:** Semua aksi admin dicatat di audit log dengan timestamp dan alasan.

### Reliability & Availability
- **Target Uptime:** 99.9% ketersediaan selama acara pemesanan tiket berlangsung.
- **Circuit Breaker + Degraded Mode:**
  - Jika Cache Cluster (Redis) tidak responsif > 100ms, Circuit Breaker terbuka.
  - **Degraded Mode:**
    - Rate Limiting: Dilemahkan (allow semua request, tapi log warning).
    - Bitmask Lock: Ditangguhkan sementara. Semua request masuk ke waiting room FIFO (di PostgreSQL).
    - Tampilkan pesan ke user: "Sistem sedang sibuk, mohon tunggu..."
  - Ketika Cache Cluster pulih, sistem kembali ke mode normal dan memproses antrean.
- **Data Backup:** Automated Snapshot database setiap jam saat high-traffic event.
- **Disaster Recovery:** Recovery Time Objective (RTO) < 15 menit, Recovery Point Objective (RPO) < 1 menit.
- **Webhook Reconciliation Worker:** Berjalan setiap 10 menit untuk memverifikasi transaksi PENDING yang mencurigakan.

### Scalability
- **Horizontal Scaling:** Stateless API Server yang dapat di-scale secara horizontal.
- **Database Scaling:** Pemisahan Read/Write Replica pada database; penggunaan cache cluster untuk operasi in-memory.

**Description:** Memahami batas sistem V1.0 dan bagaimana mengembangkannya untuk skala lebih besar.

### Current Design Capacity (V1.0)
| Component | Capacity | Bottleneck |
|-----------|----------|------------|
| API Gateway (Golang) | 50.000 RPS | CPU-bound |
| Redis Bitmask Lock | 100.000 ops/sec | Single-threaded |
| PostgreSQL | 10.000 writes/sec | Disk I/O |
| **System Ceiling** | **~20.000 RPS** | **PostgreSQL writes** |

### How to Scale Beyond 20.000 RPS (V2.0+)

| Scaling Action | Description | When to Apply |
|----------------|-------------|---------------|
| **Read Replicas** | Pisahkan query SELECT ke replica | Saat SELECT queries > 5.000/sec |
| **Sharding by Event** | Partisi data per event ke database berbeda | Saat total events > 50/month |
| **Async Write Queue** | Tulis data non-kritis (logs, analytics) via queue | Saat write > 10.000/sec |
| **Redis Cluster** | Partisi Bitmask Locking ke multiple Redis nodes | Saat satu Redis > 80% CPU |
| **Kafka for Event Streaming** | Ganti RabbitMQ dengan Kafka | Saat events > 100.000/sec |
| **Microservices Split** | Pisahkan Auth, Booking, Payment, Analytics | Saat tim > 10 developers |

## 🚨 RISKS & MITIGATION

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|-----------|
| **Payment Gateway Webhook Timeout / Hilang** | Medium | High | Terapkan Webhook Reconciliation Worker (polling ke Payment Gateway setiap 10 menit) + Idempotency Keys. |
| **Bypass Bot via Scripting Direct API** | High | Critical | Wajibkan Queue Token Validation bertanda tangan di layer gateway. |
| **Cache Cluster Failure (Redis Down)** | Low | Critical | Circuit Breaker + Degraded Mode (fallback ke PostgreSQL, antrean FIFO). Sistem kembali normal otomatis setelah Redis pulih. |
| **Race Condition pada Split-Pay Expiry** | Medium | High | Gunakan Idempotent Lazy-Check Pattern untuk menghindari kompleksitas pembatalan pesan. |
| **Bitmask Lock Overlap Conflict** | High | Medium | Partisi denah kursi per section untuk mengurangi ukuran bitmask dan meminimalisir konflik. |
| **Payout API Gagal (F005)** | Medium | Medium | Retry dengan exponential backoff (3x), jika gagal → status PENDING_PAYOUT dan admin melakukan manual reconciliation via F006. |
| **Admin Salah Input Harga** | Medium | High | Admin Emergency Tools (Bulk Cancellation + Refund + Audit Log) di F006. |
| **Webhook Reconciliation Worker Overload** | Low | Medium | Batasi jumlah transaksi yang diproses per siklus (misal 100 per 10 menit). Prioritaskan yang paling tua. |
| **Scanner Offline Data Loss** | Medium | Medium | Scanner menyimpan data secara lokal (SQLite) dan disinkronisasi saat online. Data tidak hilang meskipun scanner mati. |
| **Feedback Loop Memberikan Rekomendasi Salah** | Low | Low | Rekomendasi bersifat advisory (tidak otomatis dieksekusi). Admin harus menyetujui sebelum diterapkan. |

## 📝 APPENDIX: GLOSSARY

| Term | Definition |
|------|-----------|
| **Bitmask Matrix** | Representasi denah kursi dalam bentuk bitmap (0=tersedia, 1=terkunci) untuk operasi cepat. |
| **Fan Score** | Skor kredibilitas pengguna berdasarkan Base Score (pra-acara) + Dynamic Score (perilaku real-time) + Loyalty Score (riwayat pembelian). |
| **Split-Pay** | Mekanisme pembayaran terpisah di mana setiap anggota grup membayar bagiannya sendiri. |
| **Bulk Payment** | Mekanisme di mana satu orang (Leader) membayar semua tiket sekaligus. |
| **Dynamic HMAC QR** | QR code yang berubah secara periodik menggunakan HMAC untuk mencegah screenshot/foto tiket. |
| **Static Fallback PIN** | PIN 12-digit statis yang dikirim via SMS/Email untuk situasi darurat (HP mati). |
| **Controlled Resale Market** | Pasar sekunder resmi dengan batas harga maksimum +10% dari harga awal. |
| **Idempotent Lazy-Check** | Pola di mana pesan delay tetap dikirim dan dieksekusi, tetapi worker hanya melakukan action jika kondisi di waktu eksekusi masih memenuhi syarat. |
| **Pre-Computed Base Score** | Skor dasar yang dihitung sebelum acara berdasarkan data statis user (umur akun, verifikasi, riwayat). |
| **Degraded Mode** | Mode operasi darurat ketika Cache Cluster down. Sistem tetap berjalan dengan performa menurun. |
| **Webhook Reconciliation Worker** | Background worker yang memverifikasi transaksi PENDING dengan memanggil Payment Gateway secara langsung. |
| **Post-Event Analytics** | Data dan insight yang dihasilkan setelah acara selesai (attendance, no-show rate, peak entry time, gate utilization). |
| **Priority Tier** | Sistem antrean prioritas di waiting room berdasarkan Loyalty Score (Tier 1 = VIP Fans, Tier 2 = Regular, Tier 3 = New Users). |
| **Feedback Loop** | Mekanisme sistem belajar dari data historis untuk memberikan rekomendasi dan otomatisasi konfigurasi. |
| **Scalability Ceiling** | Batas maksimum kapasitas sistem sebelum perlu dilakukan perubahan arsitektur. |
| **Developer Experience** | Kemudahan bagi developer untuk memahami, mengembangkan, dan memelihara kode. |

3.1 FROM PRD v6.0 §F002 — BITMASK ATOMIC LOCKING SPEC
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION:
  Mengunci N-kursi berurutan secara atomik dalam denah panggung menggunakan 
  operasi bitwise di memori. Denah kursi dipartisi per section untuk mengurangi 
  konflik, dan mapping kursi dibuat immutable setelah layout diterbitkan.

INPUTS:
  - Event ID (UUID)
  - Section ID (string)
  - Seat IDs (Array of Integers / Bit Positions)
  - User Queue Token (Valid JWT)

PROCESS:
  1. Engine memuat Bitmask Matrix dari cache berdasarkan Section ID 
     (setiap section adalah key terpisah).
  2. Sistem menjalankan operasi bitwise untuk memeriksa ketersediaan N kursi 
     secara simultan dalam satu operasi atomic.
  3. Jika seluruh kursi tersedia (bernilai 0), sistem mengubah status kursi 
     menjadi terkunci (bernilai 1) dan menyimpan pemetaan ID Pengguna dengan 
     TTL 180 detik.
  4. Sistem mengirim event payload ke Message Broker untuk memicu proses 
     Split-Pay (F003).

OUTPUTS:
  - Booking Reference ID
  - Seat Allocation Map (JSON response)
  - Expiry Timestamp (Epoch ISO8601)

EDGE CASES:
  - Partial Seat Lock Conflict (1 dari 4 kursi tiba-tiba diambil pengguna 
    lain) → Sistem langsung membatalkan lock untuk seluruh N kursi 
    (Rollback All) dan mengembalikan pesan "Seats No Longer Available".
  - Cache Cluster Failure → Sistem masuk ke Degraded Mode.

3.3 FROM LOGIC_FLOW v1.4 §3 — FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

STATE DEFINITION (Seat & Booking):

  | State              | Description                                          |
  |--------------------|------------------------------------------------------|
  | AVAILABLE          | Bit = 0, kursi kosong                                |
  | LOCKED             | Bit = 1, kursi sedang di-lock (TTL 3 menit)          |
  | PENDING_SPLIT_PAY  | Kursi terkunci, menunggu pembayaran grup             |
  | CONFIRMED          | Sudah dibayar, tiket valid                           |
  | RESALE_PENDING     | Sedang dalam proses resale                           |
  | CANCELLED          | Dibatalkan                                           |
  | USED               | Sudah di-scan di gate                                |

CRITICAL — UNIFORM NATIVE REDIS BITMAP (FIXED v1.4):
  - WAJIB menggunakan native Redis Bitmap (GETBIT/SETBIT)
  - OFFSET: 0-based (posisi kursi 1 → offset 0)
  - TIDAK PERNAH menggunakan manipulasi string ASCII pada key bitmap

ATOMIC LOCK SCRIPT (lock_seats.lua) — Pseudocode:

  Input:
    KEYS[1] = "seats:{event_id}:{section_id}:v{layout_version}"
    ARGV[1] = JSON array seat positions, e.g. [10,11,12,13]
    ARGV[2] = booking_id
    ARGV[3] = JSON booking data

  Output:
    JSON { status: SUCCESS|CONFLICT, position?, booking_id? }

  Algorithm:
    Step 1: For each seat position `pos`:
              IF GETBIT(KEYS[1], pos - 1) == 1:
                RETURN { status: 'CONFLICT', position: pos }
    Step 2: For each seat position `pos`:
              SETBIT(KEYS[1], pos - 1, 1)
    Step 3: SET "booking:{ARGV[2]}" = ARGV[3] EX 180
    Step 4: RETURN { status: 'SUCCESS', booking_id: ARGV[2] }

  Atomicity guarantee: single Redis Lua execution (no interleaving).

ATOMIC RELEASE SCRIPT (release_seats.lua) — Pseudocode:

  Input:
    KEYS[1] = "seats:{event_id}:{section_id}:v{layout_version}"
    ARGV[1] = JSON array seat positions
    ARGV[2] = booking_id

  Output:
    JSON { status: SUCCESS, released: <count> }

  Algorithm:
    released = 0
    For each seat position `pos`:
      IF GETBIT(KEYS[1], pos - 1) == 1:
        SETBIT(KEYS[1], pos - 1, 0)   ← granular per-bit, no overwrite
        released = released + 1
    DEL "booking:{ARGV[2]}"
    RETURN { status: 'SUCCESS', released: released }

SEQUENCE FLOW (Booking Lock):

  [USER REQUEST: BOOK SEATS]
    │
    ▼
  Step 1: VALIDATE INPUT
    - Validasi Queue Token (JWT signature & expiry)
    - Single-use token check: SET "queue_token:used:{jti}" 1 NX EX 300
        └─> Jika return nil → HTTP 409 CONFLICT (TOKEN_ALREADY_USED)
    - Validasi Event ON_SALE
    - Validasi Section ID + layout_version
    - Validasi seat positions 1..total_seats
    - Validasi len(seat_positions) <= max_group_seats (10)
    │
    ▼
  Step 2: EXECUTE LUA SCRIPT (atomic)
    - If status == CONFLICT → 409 (rollback ALL, no partial lock)
    - If status == SUCCESS → proceed
    │
    ▼
  Step 3: CREATE BOOKING RECORD (Postgres INSERT)
    - INSERT bookings dengan payment_status = 'PENDING'
    - expires_at = NOW() + 180s
    - If DB fails → release Redis bits (rollback)
    │
    ▼
  Step 4: SEND DELAYED MESSAGE (F003)
    - Publish { type: 'RELEASE_SEAT_CHECK', booking_id } ke delayed_exchange
    - x-delay = 180s
    - Idempotent Lazy-Check pattern (tidak pernah dibatalkan)
    │
    ▼
  [RETURN RESPONSE]
    - Booking ID, Seat Allocation Map, Expiry Timestamp

EDGE CASES:

  | Edge Case                                    | Handling                        |
  |----------------------------------------------|---------------------------------|
  | Partial conflict (1 dari 4 kursi diambil)    | Lua rollback all, no partial    |
  | Redis Cluster Failure                        | Circuit Breaker → Degraded Mode |
  | Immutability Violation (layout berubah)      | Reject via layout_version check |
  | TTL 180 detik habis (belum bayar)            | Delayed msg worker (FASE 4)     |
  | Queue Token Replay Attack                    | Single-use via Redis SET NX     |

3.4 FROM LOGIC_FLOW v1.4 §9.2, §9.3 — QUEUE TOKEN + BIT RELEASE
────────────────────────────────────────────────────────────────────────────────

SINGLE-USE QUEUE TOKEN GUARD:

  [SAAT TOKEN DIBUAT di F001.3 Step 8]
    ├─> Generate JWT dengan payload:
    │    { user_id, tier, final_score, jti, exp: NOW() + 5 minutes }
    └─> jti = UUID v4

  [SAAT TOKEN DIVALIDASI di F002.3 Step 1]
    ├─> Validasi signature & expiry (standar JWT)
    ├─> Cek single-use di Redis:
    │    SET "queue_token:used:{jti}" 1 NX EX 300
    │    └─> Return "OK"    → token belum dipakai, lanjutkan
    │    └─> Return nil     → token sudah dipakai, HTTP 409 CONFLICT
    └─> TTL 300 detik (sama dengan expiry JWT)

GRANULAR BIT RELEASE:

  [SAAT RELEASE SEATS (Rollback / Expired / Admin Cancel)]
    └─> FOR EACH seat_position IN seats_to_release:
          SETBIT(key, seat_position - 1, 0)   ← 0 = AVAILABLE

  [SAAT CHECK SEATS AVAILABILITY]
    └─> GETBIT(key, seat_position - 1)

  [SAAT LOCK SEATS]
    └─> SETBIT(key, seat_position - 1, 1)

  NOTE: Release per-bit via SETBIT. TIDAK PERNAH overwrite seluruh bitmap.
  Race condition-safe karena per-bit granular dan Redis single-threaded.

3.5 FROM TDD v1.10 §6.2 — IMPLEMENTATION FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

LOCK SEATS SERVICE — Flow:

  Function LockSeats(ctx, req):
    Step 1: Validate Queue Token (single-use, SET NX EX 300)
              - if fail → return ErrTokenAlreadyUsed

    Step 2: Get section.layout_version from DB
              - if fail → return err

    Step 3: Compute Redis key
              key = "seats:{event_id}:{section_id}:v{layout_version}"
              args = [seat_positions_json, booking_id, booking_data_json]

    Step 4: Execute Lua script via Circuit Breaker wrapper
              - if Circuit OPEN → fallbackLockSeats (DB Queue, return QUEUED)
              - if CONFLICT → return ErrSeatsNotAvailable (409)
              - if SUCCESS → continue

    Step 5: Build booking record (ID, EventID, SectionID, LeaderUserID,
              SeatPositions, TotalSeats, TotalAmount, PaymentMode,
              PaymentStatus='PENDING', ExpiresAt=NOW()+180s)
              CATATAN: layout_version BUKAN field booking (runtime var only,
              tidak ada kolom di bookings table per DATABASE_SCHEMA v2.9).

    Step 6: INSERT booking ke DB
              - if DB fail → release Redis bits (compensation)
              - if DB success → continue

    Step 7: Publish delayed message ke RabbitMQ
              queue = "release_seat_check"
              delay = 180 seconds
              payload = { type: 'RELEASE_SEAT_CHECK', booking_id }

    Step 8: Return LockResponse { BookingID, ExpiresAt }

  Return: LockResponse atau error

RELEASE SEATS SERVICE — Flow:

  Function releaseSeats(ctx, eventID, sectionID, bookingID, seats, layoutVersion):
    key = "seats:{event_id}:{section_id}:v{layout_version}"
    args = [seats_json, booking_id]
    Execute release Lua script
    Return error jika gagal

FALLBACK (Circuit Breaker OPEN) — Flow:

  Function fallbackLockSeats(ctx, req):
    - Insert request ke DB Queue (bookings_queue atau FIFO pattern)
    - Return LockResponse {
        BookingID: req.BookingID,
        Status: "QUEUED",
        Message: "System is busy, your booking is queued",
        EstimatedWait: 30
      }

10.2 NOTES UMUM
────────────────────────────────────────────────────────────────────────────────

- FASE 3 adalah fitur bisnis PERTAMA yang menyentuh uang (booking = intent 
  to pay). Kualitas concurrency HARUS sempurna.

- Redis bitmap adalah SOURCE OF TRUTH untuk lock state. DB bookings hanya 
  untuk audit + audit trail. Kalau Redis di-restore, rebuild dari tickets 
  (lihat DRP v1.2 §5.2 Step 7).

- Layout version immutability: setiap section punya layout_version. Kalau 
  admin ubah layout, version ++ dan key baru dibuat. Key lama akan 
  auto-cleanup (no TTL needed — Redis key tetap ada tapi tidak di-akses).

- PENTING: Booking struct TIDAK punya field layout_version (per DATABASE_SCHEMA 
  v2.9 — bookings table TIDAK ada kolom layout_version). Layout version 
  disimpan sebagai RUNTIME VARIABLE di service, dipakai untuk membentuk 
  Redis key. Jangan masukkan ke struct atau INSERT statement.

- Postgres transactions: booking INSERT harus commit SETELAH Redis lock 
  sukses. Kalau DB fail, release Redis bit (rollback). Pattern ini ada di 
  TDD v1.10 §6.2.

- Delayed message TIDAK PERNAH dibatalkan (Idempotent Lazy-Check pattern). 
  FASE 4 worker akan cek booking status di T+3min: kalau sudah PAID → no-op; 
  kalau masih PENDING → rollback.

- Concurrency test WAJIB: 10-100 users lock seat yang sama. Hasil harus 
  1 winner, sisanya 409. Ini bukti atomic lock works.

- Chaos test WAJIB: Redis down → Circuit Breaker OPEN → DB Queue fallback. 
  User dapat response "QUEUED" dengan estimasi wait 30s.

- Frontend screens (4.1, 4.2) di FASE 3 hanya SKELETON. Implementasi penuh 
  di FASE 9.

- Rate limit per user: identify via JWT sub. Kalau user tidak authenticated 
  (public endpoints), fallback IP.

- Idempotency key WAJIB: kalau user retry POST /seats dengan key sama 
  dalam 24 jam, return cached response (tidak double-lock).

- NO CODE INJECTION (per AI ROADMAP GUARDRAIL §2.2): Section 3.3 & 3.5 
  hanya berisi pseudocode + flow summary (bukan Lua script utuh atau Go 
  handler utuh). Detail implementasi ada di TDD v1.10 §6.2. Eksekutor 
  implementasi mengikuti panduan pseudocode + cross-reference TDD.

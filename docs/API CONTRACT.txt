2. AUTHENTICATION & AUTHORIZATION
================================================================================

2.1 AUTHENTICATION FLOW
────────────────────────────────────────────────────────────────────────────────

METHOD: JWT (JSON Web Token) — RS256 (asymmetric signing)
EXPIRATION:
  - access_token: 1 hour
  - refresh_token: 7 days

JWT PAYLOAD (Claims)
{
  "sub": "uuid-user-id",
  "email": "user@example.com",
  "role": "customer|event_organizer|gate_staff|admin",
  "tier": "TIER_1|TIER_2|TIER_3",
  "token_type": "access|refresh",
  "jti": "uuid-unique-jti",
  "iat": 1723637400,
  "exp": 1723641000,
  "iss": "e-tix-flash"
}

TOKEN DELIVERY
- Response: Authorization: Bearer <access_token>
- Request: Header Authorization: Bearer <access_token>
- Storage (PWA): Secure storage (flutter_secure_storage / localStorage with care)
- Refresh: POST /auth/refresh-token with refresh_token (with rotation)

2.2 ROLE-BASED ACCESS CONTROL (RBAC)
────────────────────────────────────────────────────────────────────────────────

USER ROLES (from users.role ENUM)
┌────────────────┬────────────────────────────────────────────────────────────┐
│ Role           │ Capabilities                                               │
├────────────────┼────────────────────────────────────────────────────────────┤
│ customer       │ Browse events, book seats, split-pay, view tickets, resale │
│ event_organizer│ Manage events, view analytics, emergency bulk cancel       │
│ gate_staff     │ Scan QR, verify PIN, offline sync                          │
│ admin          │ Full system access, ledger audit, user management, reversal│
└────────────────┴────────────────────────────────────────────────────────────┘

ENDPOINT-LEVEL RBAC
All endpoints validate:
1. Token validity (signature, expiration)
2. Token type (`token_type == "access"`)
3. User status (ACTIVE, not SUSPENDED/FROZEN/DELETED)
4. Role requirement (e.g., customer-only endpoint)

RLS (Row-Level Security) enforced at database layer:
- SELECT: Users see only own data (id = auth.uid())
- INSERT: Wallet/booking creation requires matching user_id
- UPDATE: Only own records can be updated
- Admin: Can query all via (auth.jwt() ->> 'role') = 'admin'

================================================================================

3.1 SUCCESS RESPONSE
────────────────────────────────────────────────────────────────────────────────

HTTP Status: 200 (GET), 201 (POST create), 202 (async processing)

Format:
{

}

3.2 ERROR RESPONSE
────────────────────────────────────────────────────────────────────────────────

HTTP Status: 4xx (client), 5xx (server)

Format:
{
  "success": false,
  "data": null,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable error message",
    "details": { /* optional extra context */ }
  },
  "meta": { ... }
}

ERROR CODES (STANDARDIZED)

| Code                                | HTTP | Meaning                                            |
|-------------------------------------|------|----------------------------------------------------|
| INVALID_REQUEST                     | 400  | Malformed request, missing field                   |
| UNAUTHORIZED                        | 401  | Missing/invalid token                              |
| TOKEN_TYPE_MISMATCH                 | 401  | Refresh token used as access token                 |
| TOKEN_BLACKLISTED                   | 401  | Refresh token revoked (rotation)                   |
| INVALID_QR_OR_TICKET_MISMATCH       | 401  | QR decoded ticket ID != request ticket ID          |
| QUEUE_TOKEN_REQUIRED                | 401  | X-Queue-Token header missing                       |
| FORBIDDEN                           | 403  | Token valid but role insufficient                  |
| NOT_FOUND                           | 404  | Resource doesn't exist                             |
| CONFLICT                            | 409  | Race condition (e.g., seat already taken)          |
| RESALE_LISTING_EXISTS               | 409  | Ticket already has active resale listing           |
| TOKEN_ALREADY_USED                  | 409  | Queue token already used (replay attack)           |
| TARGET_USER_INACTIVE_OR_SUSPENDED   | 422  | Bulk assign target not ACTIVE/blacklisted          |
| UNPROCESSABLE_ENTITY                | 422  | Business logic violation                           |
| RATE_LIMIT_EXCEEDED                 | 429  | Too many requests                                  |
| INTERNAL_ERROR                      | 500  | Unexpected backend error                           |
| SERVICE_UNAVAILABLE                 | 503  | Database down or Redis circuit breaker open        |

4. COMMON HEADERS & VALIDATION
================================================================================

4.1 REQUEST HEADERS
────────────────────────────────────────────────────────────────────────────────

Required (All endpoints):
- Authorization: Bearer <access_token>  (except public endpoints)
- Content-Type: application/json

Required (Idempotent operations):
- X-Idempotency-Key: <UUID> — Required for all POST mutations
  * Idempotency guaranteed for 24 hours
  * Same key + same payload = identical response
  * Same key + different payload = HTTP 409 IDEMPOTENCY_CONFLICT
  * L1: Redis cache (24h TTL)
  * L2: PostgreSQL (idempotency_key column in payment_obligations)

Required (Booking operations):
- X-Queue-Token: <jwt-queue-token> — Required for POST /events/{eid}/sections/{sid}/seats
  * JWT Queue Token obtained from /queue/verify-captcha or /queue/status
  * Single-use guard: SET queue_token:used:{jti} 1 NX EX 300
  * If reused → HTTP 409 TOKEN_ALREADY_USED

Required (Admin endpoints):
- X-Admin-2FA-Token: <token> — 2FA verification
  * 3 failed attempts → 15 min lockout
  * Redis + PostgreSQL dual-write

Optional (Tracing):
- X-Request-ID: <UUID> — For request tracking (generated if missing)

4.2 REQUEST VALIDATION
────────────────────────────────────────────────────────────────────────────────

All inputs validated server-side:

Numeric Fields
- amount, price, fare: Must be >= 0, numeric precision to 2 decimals
- Use decimal.Decimal in Go (shopspring/decimal)
- Currency: All amounts in IDR (Rp) as integers (no decimals in JSON)

String Fields
- email: RFC 5322 compliant
- phone: +62 prefix optional, 10-15 digits, validated via regex
- UUID: RFC 4122 format
- Enum fields: Strict matching (e.g., role from ENUM list only)

Date/Time
- All timestamps: ISO 8601 with timezone (TIMESTAMPTZ in DB)
- Timezone: UTC (no client-side timezone)
- Format: "2026-09-10T10:30:45.123Z"

4.3 RESPONSE VALIDATION
────────────────────────────────────────────────────────────────────────────────

All responses guarantee:
- Consistent JSON structure (success/error/meta)
- Complete fields (no partial null objects)
- Type safety (no string where number expected)
- Enum values match database ENUM definitions

  Auth: Required (JWT, admin)
  Rate Limit: 30 req/min per admin
  Idempotency: REQUIRED

Headers:
- Authorization: Bearer <admin_token>
- X-Admin-2FA-Token: <2fa_verification_token>

Description (v1.2 — clarified):
  Trigger refund via Payment Gateway untuk payment_obligation yang sudah PAID.
  Tidak ada compensating ledger entry internal — Payment Gateway adalah source of truth.

Request:
{
  "transaction_id": "uuid-payment-obligation-456",
  "reason": "Customer dispute — unable to attend, refund per policy"
}

Processing:
1. Validate 2FA token (lockout: 3 failed → 15 min)
2. Validate payment_obligation exists, status = 'PAID', not yet refunded
3. Call Payment Gateway refund API using `external_transaction_id`
4. UPDATE payment_obligations SET status = 'REFUNDED', refunded_at = NOW(),
   refund_transaction_id = <gateway_refund_id>
5. Trigger handle_ticket_cancellation_on_refund() → tickets.status = 'CANCELLED'
6. INSERT INTO admin_actions (action_type = 'MANUAL_REFUND', ...) — immutable audit

Success (200 OK):
{
  "success": true,
  "data": {
    "payment_obligation_id": "uuid-payment-obligation-456",
    "status": "REFUNDED",

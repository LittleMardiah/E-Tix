1.4 DRP PRINCIPLES
────────────────────────────────────────────────────────────────────────────────

✅ Fail-Safe, Not Fail-Down: Setiap komponen punya fallback (Circuit Breaker → DB Queue)
✅ Idempotent Recovery: Semua operasi recovery dapat diulang tanpa efek samping
✅ Payment Gateway is Authoritative: Recovery pembayaran selalu cross-check ke Payment Gateway
✅ Data Integrity First: Tidak ada "partial recovery" — all-or-nothing untuk transaksi
✅ Observable: Setiap langkah recovery ter-log (Zap JSON) & ter-metric (Prometheus)
✅ State Consistency: Setiap restore PostgreSQL WAJIB diikuti purge + rebuild Redis state
   untuk mencegah desync antara DB (state lampau) dan Redis (state kini).

3.2 SEVERITY LEVELS DEFINITION
────────────────────────────────────────────────────────────────────────────────

CRITICAL (RTO: < 15 menit, RPO: 0-1 menit)
  Skenario yang langsung mengancam core business operations.
  Data loss minimal tidak dapat diterima.
  Wajib trigger Incident Response (SECURITY_SPEC v1.4 §13).
  Contoh: PostgreSQL corruption, JWT compromise, DB credential leak,
  full-region outage, Payment Gateway extended outage.

HIGH (RTO: 5-15 menit, RPO: ≤ 5 menit)
  Skenario significant impact tapi bukan immediate threat ke core business.
  Bisa direcover via fallback atau alternative means.
  Contoh: Redis cluster total failure, RabbitMQ failure, backend region down,
  DDoS attack, DNS/TLS failure, CloudAMQP quota exceeded.

MEDIUM (RTO: 15-60 menit, RPO: ≤ 1 jam)
  Impact terbatas atau partial functionality loss.
  Contoh: Frontend region failure, Payment Gateway short outage,
  SMS/Email provider outage.

LOW (RTO: > 1 jam, RPO: ≤ 1 hari)
  Minimal business impact, dapat di-defer.
  Contoh: FCM push provider outage (bisa di-retry), non-critical UI issues.

4.1 BACKUP ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

4.1.1 DATABASE BACKUPS (Supabase PostgreSQL)

Strategy:       Full Daily + Point-in-Time Recovery (PITR) + Hourly Snapshot (High-Traffic)
Tool/Method:    Supabase Automated Backups + pg_basebackup + WAL archiving

Configuration:
  - Full Backup Frequency:      Daily (00:00 UTC, off-peak)
  - PITR Granularity:           Up to 7 days (Supabase Pro tier)
  - Hourly Snapshot:            Aktif selama flash sale period (dari PRD NFR)
  - Retention Period:           7 days (PITR), 30 days (daily snapshots)
  - Storage Location:
      * Primary:   Supabase managed storage (same region as DB)
      * Secondary: Manual export to AWS S3 (different region) — weekly
  - Verification:               Automated restore test — mingguan
  - Backup Size Estimation:     ~5 GB per 100k bookings (estimate)
  - RPO Achieved:               ≤ 1 menit (via WAL streaming)
  - RTO Achieved:               ≤ 15 menit (via snapshot restore)

Tables Covered (12 dari DATABASE_SCHEMA v2.9):
  users, events, sections, bookings, payment_obligations, tickets,
  ticket_scans, resale_transactions, admin_actions, insights,
  blacklist, system_config

Critical Constraints:
  - Transaksi keuangan WAJIB idempotent setelah restore (via payment_obligations.idempotency_key)
  - Rekonsiliasi pembayaran WAJIB setelah restore (via Webhook Reconciliation Worker)
  - RLS policies WAJIB ter-restore bersamaan (bundle dalam migration)
  - Redis state WAJIB purge + rebuild setelah restore (untuk cegah desync dengan PostgreSQL)

4.1.2 APPLICATION & CODE BACKUPS

Version Control:        GitHub (private repo: e-tix-flash)
Backup Frequency:       Real-time (setiap commit/push)
Repository Mirroring:   GitHub + local bare clone (offline backup)
Configuration Files:
  - .env.example         → repo (template only, no secrets)
  - migrations/*.sql     → repo (versioned)
  - Dockerfile           → repo
  - docker-compose.yml   → repo
Secrets Management:
  - Render.com Environment Variables (encrypted at rest)
  - Local .env (never committed — .gitignore)
  - Backup: exported encrypted ke password manager (Bitwarden/1Password) — bulanan

4.1.3 REDIS STATE BACKUPS (Upstash)

Strategy:       Snapshot-based (Upstash managed)
Frequency:      Automatic (Upstash default) + manual backup sebelum flash sale
Retention:      7 days
Critical Note:
  Redis state TIDAK critical untuk data permanen — bisa di-rebuild dari PostgreSQL.
  Yang perlu recoverable:
    - seats:{event_id}:{section_id}:v* → rebuild dari tickets.status + Redis Lua init
    - booking:{booking_id}             → rebuild dari bookings table (status=PENDING)
    - queue_token:used:{jti}           → NON-CRITICAL (TTL 300s, akan expire otomatis)
    - idempotency:{key}                → L2 PostgreSQL (payment_obligations.idempotency_key)
    - refresh_blacklist:{jti}          → NON-CRITICAL (re-login acceptable)

4.1.4 RABBITMQ STATE BACKUPS (CloudAMQP)

Strategy:       CloudAMQP managed (durable queues)
Critical Note:
  Delayed messages TIDAK perlu di-backup — semua async operations idempotent.
  Jika RabbitMQ hilang:
    - Booking expiry    → di-recover via admin_actions + manual trigger
    - Resale expiry     → di-recover via scheduled scan (SELECT yang RESERVED expired)
    - Reconciliation    → di-recover via Webhook Reconciliation Worker manual trigger
    - Fan score         → NON-CRITICAL (base score ada di PostgreSQL)

5.2 PLAYBOOK #1: PostgreSQL PRIMARY FAILURE / CORRUPTION
────────────────────────────────────────────────────────────────────────────────

Severity: CRITICAL

Symptoms / Detection:
  - Alert: `database_connection_pool_exhausted` (Prometheus) — active conns >= 14 of 15
  - Alert: `http_requests_total{status=~"5.."}` error rate > 5% in 5-min window
  - Application log (Zap): `error connecting to postgres: connection refused` atau
    `pgx: FATAL: the database system is in recovery mode`
  - /healthz/readiness → `{"checks": {"database": "fail"}}` (HTTP 503)

Impact Assessment:
  - Affected Systems: Seluruh backend (REST API), semua workers, seluruh transaksi
  - User Impact: Total service unavailability (browse, booking, payment, gate scan)
  - Business Impact: Total revenue loss during outage, ticket sales halted, SLA breach

Immediate Actions (First 15 minutes):
  1. Incident Commander (M. Arif Aulia) konfirmasi issue via Supabase Dashboard + alert
  2. Aktifkan Circuit Breaker (jika belum) → backend masuk Degraded Mode (LOGIC_FLOW §9.4)
     → Semua request masuk PostgreSQL FIFO queue (bukan Redis bitmap)
  3. Kirim notifikasi ke user via status banner: "Sistem sedang sibuk, mohon tunggu..."
  4. Dokumentasikan timestamp mulai outage

Recovery Steps:

  Phase 1 — Preparation:
    - [ ] Cek Supabase Dashboard: apakah ada indikasi maintenance/incident dari Supabase
    - [ ] Cek Supabase Status Page (status.supabase.com)
    - [ ] Identifikasi apakah korupsi data atau hardware failure
    - [ ] Tentukan backup target: latest snapshot atau PITR ke timestamp tertentu
          (PITR ke timestamp sebelum corruption = best practice)

  Phase 2 — Execution (via Supabase Dashboard / CLI):

    Step 1: Jika Supabase managed failover, tunggu auto-recovery (biasanya < 15 min).
            Verifikasi: Supabase Dashboard → Database → Health.

    Step 2: Jika perlu PITR restore manual:
            Supabase Dashboard → Database → Backups → Point in Time Recovery.
            Pilih timestamp: T-minus-corruption (mis. 2 menit sebelum alert fire).
            Konfirmasi restore (akan recreate database instance).

    Step 3: Setelah restore selesai, jalankan migration untuk memastikan schema up-to-date:

            migrate -path ./migrations -database $DATABASE_URL up

    Step 4: Verify critical tables exist (12 tabel):

            psql $DATABASE_URL -c "\dt"

    Step 5: Verify RLS policies aktif:

            psql $DATABASE_URL -c "SELECT tablename, rowsecurity FROM pg_tables WHERE schemaname='public';"

    Step 6: Verify SYSTEM_USER_UUID:

            psql $DATABASE_URL -c "SELECT id, role FROM users WHERE id='00000000-0000-0000-0000-000000000000';"

    Step 7 (WAJIB — NEW v1.2): Purge Stale Redis Cache & Rebuild State
            Konteks: PITR restore mundur ke T-minus-corruption (mis. 2 menit lalu),
            tetapi Redis masih menyimpan state bitmask dari titik "future" (T).
            Ini menyebabkan desync antara DB (state lampau) dan Redis (state kini).
            WAJIB purge + rebuild:

            7a. Purge keyspace yang stale (PILIHAN UTAMA — targeted delete):
                redis-cli -u $REDIS_URL --scan --pattern 'seats:*' | xargs -r redis-cli -u $REDIS_URL DEL
                redis-cli -u $REDIS_URL --scan --pattern 'booking:*' | xargs -r redis-cli -u $REDIS_URL DEL

                ⚠️ WARNING: FLUSHDB akan wipe SEMUA keyspace, termasuk:
                    - rate:{client_id}          → rate limit reset (acceptable)
                    - refresh_blacklist:{jti}   → refresh token blacklist hilang
                                                  (dampak: user dengan refresh token yang
                                                  sudah diblacklist bisa refresh lagi)
                    - idempotency:{key}         → L1 cache hilang (L2 PostgreSQL tetap ada)
                    - user:score:*              → fan score hilang (rebuild dari users.base_score)
                Gunakan HANYA jika targeted delete tidak feasible.

            7c. Rebuild state dari PostgreSQL hasil restore
                (lihat Playbook #2 Phase 2 Step 3 untuk detail):
                - seats:* bitmap → rebuild dari tickets.status
                - user:score:*:base → rebuild dari users.base_score
                - Keys L1 idempotency tidak perlu rebuild (L2 PostgreSQL tetap authoritative)

            7d. Verifikasi desync hilang:

                - Cek GETBIT seats:{event_id}:{section_id}:v{n} {pos-1} → harus return 1

5.3 PLAYBOOK #2: REDIS CLUSTER TOTAL FAILURE
────────────────────────────────────────────────────────────────────────────────

Severity: HIGH

Symptoms / Detection:
  - Alert: `circuit_breaker_state{name="Redis"} == 1` (OPEN) selama > 60 detik
  - Application log: `redis: connection refused` atau `i/o timeout`
  - Upstash Status Page (status.upstash.com) menunjukkan incident

Impact Assessment:
  - Affected Systems: Bitmask locking, rate limiting, idempotency L1, fan score
  - User Impact: Booking flow degraded (masuk DB FIFO queue), rate limit dilonggarkan
  - Business Impact: Booking tetap bisa jalan (degraded mode), tapi throughput turun

Immediate Actions:
  1. Circuit Breaker AKAN auto-trigger (LOGIC_FLOW §9.4) — pastikan sudah aktif
  2. Backend otomatis masuk Degraded Mode: rate limit longgar, bitmap lock ditangguhkan,
     semua request masuk PostgreSQL FIFO queue
  3. Banner user: "Sistem sedang sibuk, mohon tunggu..."
  4. Cek Upstash Status Page

Recovery Steps:

  Phase 1 — Preparation:
    - [ ] Identifikasi apakah Upstash managed outage atau Redis instance issue
    - [ ] Siapkan rebuild script (redis_seats_rebuild.go — dari tickets.status)

  Phase 2 — Execution:

    Step 1: Jika Upstash managed outage → tunggu auto-recovery.
            Monitor: Upstash Dashboard + circuit_breaker_state metric.

    Step 2: Jika Redis instance corrupt → re-provision via Upstash Dashboard.
            Setelah provision selesai, update REDIS_URL env var di Render.com.

    Step 3: Rebuild Redis state (critical keyspaces) — dengan DEL dulu untuk
            memastikan key bersih dari sisa bit korup:

            Untuk SETIAP section:
              DEL "seats:{event_id}:{section_id}:v{layout_version}"
              Lalu untuk setiap ticket dengan status IN
              ('CONFIRMED','LOCKED','PENDING_SPLIT_PAY','RESALE_PENDING','USED'):
                SETBIT "seats:{event_id}:{section_id}:v{layout_version}" {pos-1} 1

            Rebuild base_score dari users.base_score:
              SET "user:score:{user_id}:base" {base_score} EX 86400

            Keys berikut NON-CRITICAL (akan expire otomatis):
              queue_token:used:{jti}    (TTL 300s)
              booking:{booking_id}      (TTL 180s)
              refresh_blacklist:{jti}   (user re-login acceptable)

    Step 4: Idempotency fallback — PENTING:
            Selama Redis down, SEMUA idempotency penanganan transaksi duplicate
            BERPIJAH 100% ke L2 PostgreSQL via payment_obligations.idempotency_key
            (LOGIC_FLOW v1.4 §9.1).
            Setelah Redis pulih, L1 idempotency cache (idempotency:{key})
            akan kembali aktif untuk fast lookup, TETAPI L2 tetap sebagai
            source-of-truth untuk konsistensi jangka panjang.
            Verifikasi: SELECT idempotency_key FROM payment_obligations
            WHERE created_at > {outage_start} — pastikan tidak ada duplicate.

    Step 5: Drain DB FIFO queue (DBQueueSyncWorker — TDD v1.10 §6.6):
            Worker auto-run setiap 30 detik saat circuit CLOSED.

  Phase 3 — Validation:
    - [ ] `circuit_breaker_state == 0` (CLOSED)
    - [ ] Test GET /events/{id}/sections/{sid}/seats → seat availability correct
    - [ ] Test POST booking → 201 (bitmap lock works)

  - Jika rebuild gagal: refresh dari Upstash snapshot (jika ada) atau rebuild ulang

     - Aktivasi Webhook Reconciliation Worker dengan interval lebih cepat (5 menit)
  3. Tracking semua PENDING obligations yang dibuat selama outage
  4. KEBIJAKAN EXPIRY (NEW v1.2 — diklarifikasi):
     - Transaksi PENDING dengan TTL 180 detik TETAP DIBIARKAN EXPIRE secara alami
       oleh BookingExpiryWorker. Alasan:
         * Kuota kursi tidak terkunci tanpa kepastian pembayaran.
         * Konsisten dengan LOGIC_FLOW v1.4 §4.3 (Idempotent Lazy-Check pattern):
           pesan delayed TIDAK PERNAH dibatalkan, worker cek status di T+3 menit
           dan eksekusi rollback jika masih PENDING.

     - Jika user sudah terlanjur bayar di Gateway saat expiry terpicu:
         * Webhook masuk → WebhookReconciliationWorker deteksi status PAID
         * Payment_obligations sudah EXPIRED → tidak auto-mutate ke PAID
         * Trigger refund otomatis via Payment Gateway (idempotency key mencegah double-refund)
         * Log ke admin_actions (action_type = 'MANUAL_REFUND') untuk audit

  Phase 1 — Preparation:
    - [ ] Track semua external_transaction_id yang stuck

  Phase 2 — Execution:

    Setelah Payment Gateway pulih:

    Step 1: Trigger manual reconciliation untuk semua payment_obligations PENDING:
            GET /transactions/{external_transaction_id} dari Gateway
              - Jika PAID    → UPDATE status = 'PAID' + log admin_actions (MANUAL_PAID)
              - Jika FAILED  → UPDATE status = 'FAILED' + rollback (release seats)
              - Jika PENDING → tunggu webhook

  Phase 3 — Validation:
    - [ ] Semua payment_obligations PENDING resolved (PAID/FAILED/EXPIRED)
    - [ ] Seats released untuk FAILED obligations
    - [ ] Users yang PAID dapat tiketnya

9.1 GLOSSARY
────────────────────────────────────────────────────────────────────────────────

- RTO (Recovery Time Objective): Waktu maksimal sistem boleh down.
  Target E-Tix Flash: < 15 menit (PRD v6.0 NFR).
- RPO (Recovery Point Objective): Data maksimal yang boleh hilang.
  Target E-Tix Flash: < 1 menit (PRD v6.0 NFR).
- Circuit Breaker: Pola resilience untuk auto-detect failure dan switch ke fallback.
  E-Tix Flash menggunakan Circuit Breaker untuk Redis (TDD v1.10 §7).
- Degraded Mode: Mode operasi saat Redis down. Semua request masuk PostgreSQL FIFO queue.
- Idempotent Lazy-Check: Pola di mana pesan delay selalu dikirim, worker cek status di T+3m.
- PITR (Point-in-Time Recovery): Restore DB ke timestamp tertentu.
  Supabase Pro tier mendukung PITR hingga 7 hari.
- RLS (Row-Level Security): PostgreSQL access control per-row. 12 tabel E-Tix Flash.
- Webhook Reconciliation Worker: Background worker yang poll Payment Gateway setiap 10 menit.
- DBQueueSyncWorker: Worker yang drain PostgreSQL FIFO queue saat Circuit Breaker CLOSED.
- Flash Sale: Periode tiket dijual cepat (high concurrency).
- Idempotency Key: Header X-Idempotency-Key untuk mencegah duplicate transaction.
- L1 / L2 Idempotency: L1 = Redis cache (fast); L2 = PostgreSQL (persistent, source-of-truth).
- x-delayed-message: RabbitMQ exchange type untuk delayed delivery.
  BUTUH plugin rabbitmq_delayed_message_exchange (bukan default).
- Purge Stale Redis Cache: Operasi menghapus keyspace Redis ('seats:*', 'booking:*')
  yang tidak cocok dengan DB hasil PITR restore (mencegah desync).
- Redis-DB Desync: Kondisi di mana state Redis tidak sinkron dengan state PostgreSQL
  (mis. setelah PITR restore mundur, Redis masih menyimpan state dari titik "future").
- Ghost Lock: Kondisi di mana kursi terkunci di Redis tetapi tidak ada transaksi di DB
  (disebabkan oleh Redis-DB desync).

9.4 RECOVERY COMMANDS REFERENCE
────────────────────────────────────────────────────────────────────────────────

DATABASE RECOVERY (Supabase PITR):

  Restore via Supabase Dashboard:
    Database → Backups → Point in Time Recovery → pilih timestamp

  Setelah restore, verify:

    psql $DATABASE_URL -c "\dt"
    psql $DATABASE_URL -c "SELECT COUNT(*) FROM users;"
    psql $DATABASE_URL -c "SELECT id, role FROM users WHERE id='00000000-0000-0000-0000-000000000000';"

  Verify RLS aktif:

    psql $DATABASE_URL -c "SELECT tablename, rowsecurity FROM pg_tables WHERE schemaname='public';"

REDIS PURGE + RECOVERY (Setelah PITR Restore — NEW v1.2):

  Step 1 — Purge keyspace stale (targeted delete):

    redis-cli -u $REDIS_URL --scan --pattern 'seats:*' | xargs -r redis-cli -u $REDIS_URL DEL
    redis-cli -u $REDIS_URL --scan --pattern 'booking:*' | xargs -r redis-cli -u $REDIS_URL DEL

  Step 2 — Emergency fallback (jika targeted delete gagal):
    ⚠️ HATI-HATI: FLUSHDB wipe SEMUA keyspace (rate, refresh_blacklist, idempotency L1, dll):

    redis-cli -u $REDIS_URL FLUSHDB

  Step 3 — Rebuild bitmap dari PostgreSQL hasil restore (per section):

    redis-cli -u $REDIS_URL DEL "seats:{event_id}:{section_id}:v{layout_version}"

    psql $DATABASE_URL -c "SELECT section_id, seat_position FROM tickets WHERE status IN ('CONFIRMED','LOCKED','PENDING_SPLIT_PAY','RESALE_PENDING','USED');"

    redis-cli -u $REDIS_URL SETBIT "seats:{event_id}:{section_id}:v{layout_version}" {pos-1} 1

  Step 4 — Rebuild base score:

    psql $DATABASE_URL -c "SELECT id, base_score FROM users;"
    redis-cli -u $REDIS_URL SET "user:score:{user_id}:base" {base_score} EX 86400

  Step 5 — Verifikasi Redis-DB consistency:

    Ambil sample 5 tickets status CONFIRMED → GETBIT harus return 1
    Ambil sample 5 tickets status AVAILABLE → GETBIT harus return 0

  Step 6 — Idempotency fallback aktif di L2 PostgreSQL selama Redis down:

    Verifikasi: SELECT idempotency_key FROM payment_obligations WHERE created_at > {outage_start}

BACKEND FAILOVER (Render.com):

  1. Buat new Web Service di region alternatif via Render.com Dashboard
  2. Link ke repo GitHub, build via Dockerfile
  3. Set env vars (dari Bitwarden backup)
  4. Update DNS via Cloudflare Dashboard:
       api.e-tix-flash.com → CNAME → {new-render-endpoint}
  5. Verify:
       curl https://api.e-tix-flash.com/healthz/readiness

SECRET ROTATION (JWT):

  Generate new RSA key pair:

    openssl genrsa -out new_private_key.pem 2048
    openssl rsa -in new_private_key.pem -pubout -out new_public_key.pem

  Update Render env vars: JWT_PRIVATE_KEY, JWT_PUBLIC_KEY
  Restart backend service
  Grace period: 1 hour (existing tokens expire)

RABBITMQ RE-PROVISION (CloudAMQP):

  1. Enable plugin rabbitmq_delayed_message_exchange via CloudAMQP Dashboard → Plugins
  2. Verify plugin aktif (rabbitmq-plugins list)
  3. Re-declare exchange: delayed_exchange (type: x-delayed-message)
  4. Re-declare queues: fan_score, release_seat_check, resale_expiry_check,
     report_generation, reconciliation_cycle

9.7 STATE CONSISTENCY POLICY (NEW v1.2)
────────────────────────────────────────────────────────────────────────────────

Setiap operasi restore PostgreSQL (PITR) WAJIB diikuti dengan:
  1. Purge Redis keyspace 'seats:*' dan 'booking:*' (targeted delete)
  2. Rebuild Redis bitmap dari tickets.status hasil restore
  3. Rebuild user:score:*:base dari users.base_score
  4. Verifikasi sample 5 tickets CONFIRMED → GETBIT = 1
  5. Verifikasi sample 5 tickets AVAILABLE → GETBIT = 0

Alasan: PITR restore mundur ke T-minus-corruption, tetapi Redis tetap di T (future).
Tanpa purge + rebuild, akan ada Ghost Lock yang menyebabkan kursi terkunci di Redis
tanpa transaksi valid di DB.

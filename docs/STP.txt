NOTES pada IT-PAY-004 (v1.1 — dipertegas):
  Skenario partial: dari 4 anggota grup, 3 bayar (status PAID), 1 tidak bayar
  sampai T+3 menit. Worker di T+3 menit mengeksekusi Idempotent Lazy-Check
  (LOGIC_FLOW §4.3):
    1. Booking status masih PENDING_SPLIT_PAY (belum CONFIRMED) → lanjut rollback
    2. Release 4 bitmask seats di Redis (granular SETBIT per seat, 0-based)
    3. UPDATE bookings SET payment_status = 'EXPIRED'
    4. UPDATE payment_obligations SET status = 'EXPIRED' (untuk yang PENDING)
    5. Auto-refund via Payment Gateway untuk 3 payment_obligations yang PAID
       (menggunakan external_transaction_id masing-masing)
    6. INSERT admin_actions (action_type = 'FORCE_RELEASE_SEAT',
       reason = 'SPLIT_PAY_TIMEOUT')
    7. Verifikasi: 3 refund transactions di Gateway (mock), 4 seats available
       kembali di Redis, 4 payment_obligations status EXPIRED

NOTES pada IT-GATE-003 (NEW v1.1):
  HMAC QR tolerance window: block-1, block, block+1 (LOGIC_FLOW §5.4).
  Kalau QR di-generate di timestamp block N, verifikasi di block N+2 (60s+)
  → signature mismatch → API_CONTRACT §11.1 → `INVALID_QR_OR_TICKET_MISMATCH`
  (401). BUKAN `EXPIRED_QR` (tidak ada di API_CONTRACT v1.2).

────────────────────────────────────────────────────────────────────────────────

FLAKY TEST DEFINITION: Test yang kadang pass, kadang fail tanpa perubahan kode.

FLAKY TEST PROCESS:
  1. Identify:   CI shows test failed, manual re-run passes
  2. Investigate: Root cause (timing, randomness, environment, network)
  3. Fix:        Stabilize (add retries, increase timeouts, reduce deps)
  4. Monitor:    Track fix success rate over time
  5. If unfixable: Mark "known flaky" dengan issue ticket

FLAKY TEST DASHBOARD:
  Track: Test name, failure rate %, last occurred, assigned to
  Goal:  < 5% of total suite

COMMON FLAKY CAUSES di E-Tix Flash:
  - Redis race condition (fix: retry with backoff)
  - RabbitMQ message delivery timing (fix: poll with timeout)
  - Payment Gateway mock latency (fix: deterministic mock)
  - Timezone-dependent tests (fix: freeze time via `clock` lib)

13.1 GLOSSARY
────────────────────────────────────────────────────────────────────────────────

- RTO (Recovery Time Objective): Waktu maksimal sistem boleh down. Target ETF: < 15 menit.
- RPO (Recovery Point Objective): Data maksimal boleh hilang. Target ETF: < 1 menit.
- Coverage: Persentase kode/fitur yang dieksekusi test. Target ETF: ≥ 85%.
- Regression: Bug yang muncul kembali pada functionality yang sebelumnya worked.
- Flaky Test: Test yang inconsistent (kadang pass, kadang fail).
- Smoke Test: Quick sanity check pada critical functionality.
- DoD (Definition of Done): Criteria yang harus terpenuhi untuk release.
- Bitmask Locking: Redis bitmap (GETBIT/SETBIT) — 0-based offset, atomic locking.
- Circuit Breaker: Resilience pattern (Redis down → DB Queue fallback).
- Idempotency Key: X-Idempotency-Key header, L1 Redis + L2 payment_obligations.idempotency_key.
- HMAC-SHA256: Signature algorithm untuk Dynamic QR + fallback PIN.
- IDOR / BOLA: Insecure Direct Object Reference / Broken Object Level Authorization.
- Fan Score: Skor user = Base Score + Dynamic Score (TIER_1/2/3).
- Ghost Lock: Kursi terkunci di Redis tanpa transaksi valid di DB.
- PITR: Point-in-Time Recovery (Supabase Pro, up to 7 days).
- rps: Requests per second.
- p95: 95th percentile latency.
- X-Queue-Token: JWT header single-use untuk booking lock.
- X-Admin-2FA-Token: Token wajib untuk admin financial mutations.
- INVALID_QR_OR_TICKET_MISMATCH: Error code 401 untuk QR invalid / expired /
  ticket ID mismatch (API_CONTRACT v1.2 §3.2). BUKAN `EXPIRED_QR` (tidak ada).
- UNPROCESSABLE_ENTITY: Error code 422 untuk business rule violation — dipakai
  untuk batch > 500 scans per request (SECURITY_SPEC v1.4 §7.2).
- Payload Too Large: HTTP standard 413 (bukan custom error code) — dikembalikan
  oleh BodySizeLimit middleware (SECURITY_SPEC v1.4 §7.2) ketika body > 1 MB.

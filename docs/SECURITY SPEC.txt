SECURITY PRINCIPLES

✅ Defense in Depth: Multiple layers (auth → validation → encryption → logging)
✅ Least Privilege: Users only access what they need (RBAC + RLS)
✅ Zero Trust: Validate everything (token, payload, rate limit, signature)
✅ Fail Secure: Errors default to deny (not allow)
✅ Audit Trail: Every mutation logged with user_id + timestamp
✅ Payment Gateway as Source of Truth: All financial mutations verifiable via
   external_transaction_id + webhook signature; no internal wallet/ledger.
✅ Data Minimization: Only collect and retain what's needed

2. AUTHENTICATION & AUTHORIZATION
================================================================================

2.1 AUTHENTICATION STRATEGY
────────────────────────────────────────────────────────────────────────────────

METHOD: JWT (JSON Web Token) with RS256 (asymmetric, RSA 2048-bit minimum)
ALGORITHM: RS256 (NOT HS256 — asymmetric keys allow public key distribution)
EXPIRATION:
  - access_token: 1 hour
  - refresh_token: 7 days (with rotation)

TOKEN CLAIMS (JWT Payload)
{
  "sub": "uuid-user-id",                    // Subject (user ID)
  "email": "user@example.com",
  "role": "customer|event_organizer|gate_staff|admin",
  "tier": "TIER_1|TIER_2|TIER_3",           // Fan Score tier
  "token_type": "access|refresh",           // Token type validation
  "jti": "uuid-unique-jti",                 // JWT ID for blacklist
  "iat": 1723637400,                        // Issued at
  "exp": 1723641000,                        // Expiration
  "iss": "e-tix-flash"
}

TOKEN STORAGE (PWA)
🔒 Browser (PWA):
  - access_token: In-memory (cleared on browser close) or sessionStorage
  - refresh_token: HttpOnly cookie (immune to XSS) — recommended
  - Never store in localStorage (XSS vulnerable)
  - Service Worker cache: NO tokens cached

REFRESH TOKEN FLOW (With Rotation)

1. Client stores refresh_token in secure storage
2. After access_token expires (1 hour), client calls:
   POST /auth/refresh-token
   Body: { "refresh_token": "..." }
3. Backend validates:
   - Verify signature (RS256 public key)
   - Check expiration
   - Check token_type == "refresh"
   - Check jti is NOT blacklisted in Redis
4. **Rotate tokens**:
   - Blacklist old refresh_token jti in Redis (TTL = remaining expiry, minimum 1 second)
   - Generate new access_token + new refresh_token
5. Return new token pair
6. If refresh fails → Force re-login

RBAC ENFORCEMENT LAYERS

Layer 1: HTTP Middleware (Gin)
  func AuthMiddleware(blacklist *TokenBlacklistService) gin.HandlerFunc {
    return func(c *gin.Context) {
      token := extractToken(c)
      claims, err := jwtService.ValidateAccessToken(token)
      if err != nil {
        c.JSON(401, ErrorResponse("UNAUTHORIZED"))
        c.Abort()
        return
      }
      // Enforce token_type
      if claims.TokenType != "access" {
        c.JSON(401, ErrorResponse("TOKEN_TYPE_MISMATCH"))
        c.Abort()
        return
      }
      // Check blacklist
      blacklisted, _ := blacklist.IsBlacklisted(ctx, claims.JTI)
      if blacklisted {
        c.JSON(401, ErrorResponse("TOKEN_BLACKLISTED"))
        c.Abort()
        return
      }
      c.Set("user_id", claims.UserID)
      c.Set("role", claims.Role)
      c.Set("tier", claims.Tier)
      c.Next()
    }
  }

Layer 2: Endpoint-Level Check (RBAC Middleware)
  func RBACMiddleware(allowedRoles ...string) gin.HandlerFunc {
    return func(c *gin.Context) {
      role := c.GetString("role")
      for _, r := range allowedRoles {
        if role == r {
          c.Next()
          return
        }
      }
      c.JSON(403, ErrorResponse("FORBIDDEN"))
      c.Abort()
    }
  }

  // Usage
  router.POST("/admin/events/:id/bulk-cancel",
    AuthMiddleware(blacklist),
    RBACMiddleware("admin", "event_organizer"),
    adminHandler.BulkCancel,
  )

2.3 PASSWORD SECURITY
────────────────────────────────────────────────────────────────────────────────

PASSWORD HASHING
  - Algorithm: bcrypt (cost factor ≥ 12)
  - Never transmitted over HTTP (HTTPS only)
  - Stored in users.password_hash (VARCHAR 255)

PASSWORD REQUIREMENTS
  - Minimum: 8 characters
  - Complexity: Mix of upper, lower, numbers, symbols
  - No common patterns (123456, password, etc.)
  - Max: 128 characters (bcrypt truncates at 72, so limit input)

NOTE (v1.3): Password change / forgot-password / reset-password endpoints
  adalah OUT OF SCOPE untuk MVP v1.0 sesuai API_CONTRACT v1.1 (hanya
  register, login, verify-otp, refresh-token, logout, users/me). Jika di
  masa depan ditambahkan, wajib melalui revisi API_CONTRACT terlebih dahulu.

3.3 SENSITIVE DATA MASKING
────────────────────────────────────────────────────────────────────────────────

IN LOGS (Prevent PII leakage)
  ✅ DO LOG:
    - user_id (UUID)
    - booking_id, ticket_id, transaction_id
    - HTTP status code, endpoint
    - Error code (INSUFFICIENT_BALANCE, etc.)
    - IP address (for security audit)
  
  ❌ NEVER LOG:
    - Full email or phone
    - Password or password_hash
    - JWT tokens (log jti only, never full token)
    - QR secret keys
    - Fallback PIN (plain-text)

HEADER SANITIZATION RULES (Middleware Log Masking)
  ✅ WAJIB: Middleware logging/recovery harus melakukan redaction otomatis pada header sensitif:
    - Authorization: Bearer <token> → Authorization: Bearer [REDACTED]
    - X-Admin-2FA-Token: <token> → X-Admin-2FA-Token: [REDACTED]
    - X-Queue-Token: <token> → X-Queue-Token: [REDACTED]
    - X-Idempotency-Key: boleh dicatat untuk audit, tetapi tidak boleh dikombinasikan dengan payload sensitif.
  ✅ DILARANG: menulis raw JWT, raw queue token, raw 2FA token ke log aggregator (stdout, file, Sentry, dsb).
  ✅ Implementasi: fungsi `SanitizeHeaders(http.Header) map[string]string` dipanggil sebelum logger menulis request/response.

IN API RESPONSES (Prevent data over-sharing)
  ✅ RETURN:
    - user_id, email (owner only)
    - ticket_id, status, event_name, seat_position
    - booking_id, total_amount, payment_status
  
  ❌ NEVER RETURN:
    - password_hash
    - Other users' data (enforced by RLS)
    - JWT tokens in response body (only at login/refresh)

4.1 INPUT VALIDATION (Defense Against Injection)
────────────────────────────────────────────────────────────────────────────────

PRINCIPLE: Whitelist & Type Enforcement

String Fields
  Email: RFC 5322 regex
    Pattern: ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$
    Max length: 255 characters
    Validation library: github.com/go-playground/validator/v10

  Phone: International format
    Pattern: ^\+?[0-9]{10,15}$
    Max length: 20
    Allowed: +62812345678 or 08123456789

  UUID: RFC 4122 v4
    Pattern: ^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    Validation: uuid.Parse(val)

  Name: Alphanumeric + spaces/hyphens
    Pattern: ^[a-zA-Z0-9\s\-']{3,255}$
    Max length: 255

  Fallback PIN: 12-digit alphanumeric
    Pattern: ^[A-Z0-9]{12}$
    Case-sensitive, uppercase only

Numeric Fields
  Amount: Non-negative integer (IDR)
    Range: 0 to 999,999,999,999 (Rp 999T)
    Type: int64 (for JSON) → decimal.Decimal (for calculation)
    Decimal places: Exactly 2

  Seat Position: Positive integer
    Range: 1 to total_seats

Enum Fields (Strict Matching)
  Status: Only values in database ENUM
    Example: ticket_status ∈ {AVAILABLE, LOCKED, PENDING_SPLIT_PAY, CONFIRMED, RESALE_PENDING, RESOLD, CANCELLED, USED}
    Validation: if !contains(validStatuses, input) { return error }

Date/Time
  Format: ISO 8601 with timezone
    Example: 2026-09-10T10:30:45.123Z
    Validation: time.Parse("2006-01-02T15:04:05.000Z07:00", input)
    Timezone: UTC only (reject other TZ)

PARAMETERIZED QUERIES (SQL Injection Prevention)

❌ NEVER:
  query := fmt.Sprintf("SELECT * FROM tickets WHERE id = '%s'", ticketID)

✅ ALWAYS:
  var ticket Ticket
  err := db.QueryRow("SELECT * FROM tickets WHERE id = $1", ticketID).
    Scan(&ticket.ID, &ticket.Status, ...)

Library: pgx/v5 (prepared statements built-in)

4.2 RATE LIMITING (DoS & API Abuse Prevention)
────────────────────────────────────────────────────────────────────────────────

ALGORITHM: Token Bucket (Redis-backed)
WINDOW: Rolling 1-minute

LIMITS BY ENDPOINT (From API Contract Section 5)

Authentication:
  POST /auth/signup: 10 req/hour per IP
  POST /auth/login: 5 req/min per IP (anti-brute-force)
  POST /auth/verify-otp: 5 req/15min per IP
  POST /auth/refresh-token: 10 req/15min per user

Queue:
  POST /queue/verify-captcha: 3 req/5min per IP

Read Operations:
  GET * (events, tickets, bookings, resale): 100 req/min per user/IP

Write Operations:
  POST /bookings (all): 10 req/min per user
  POST /resale (all): 10 req/min per user
  POST /admin (all): 30 req/min per admin

Gate Operations:
  POST /gate (all): 180 req/min per gate staff

IMPLEMENTATION (Redis-backed Token Bucket)
  func RateLimitMiddleware(limit int, window time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
      key := "rate:" + getClientID(c)  // user_id or IP
      
      val, _ := redisClient.Incr(ctx, key).Result()
      if val == 1 {
        redisClient.Expire(ctx, key, window)
      }
      
      remaining := limit - int(val)
      c.Header("X-RateLimit-Limit", strconv.Itoa(limit))
      c.Header("X-RateLimit-Remaining", strconv.Itoa(remaining))
      c.Header("X-RateLimit-Reset", strconv.Itoa(int(time.Now().Add(window).Unix())))
      
      if val > int64(limit) {
        c.JSON(429, ErrorResponse("RATE_LIMIT_EXCEEDED"))
        c.Abort()
        return
      }
      c.Next()
    }
  }

GRACEFUL DEGRADATION
  If Redis down:
    - Fail OPEN (allow request) with warning log
    - Continue without rate limiting (availability > security)
    - Alert admin to fix Redis

5.2 QUERY SECURITY & DEADLOCK PREVENTION
────────────────────────────────────────────────────────────────────────────────

STATEMENT TIMEOUT (Prevent Hanging Locks)

  BEGIN;
    SET LOCAL statement_timeout = '3000ms';  -- 3-second timeout
    SELECT * FROM bookings WHERE id = $1 FOR UPDATE;
    -- ... transaction logic
  COMMIT;

  If lock cannot be acquired in 3s → Connection timeout
  → Automatic retry in application layer (3x max)

DEADLOCK PREVENTION (Golang Implementation)

  // CRITICAL: Sort resource IDs to prevent circular lock ordering
  obligationIDs := []uuid.UUID{obligationA, obligationB}
  sort.Slice(obligationIDs, func(i, j int) bool {
    return obligationIDs[i].String() < obligationIDs[j].String()
  })
  
  rows, err := tx.QueryContext(ctx, `
    SELECT id, amount, status FROM payment_obligations
    WHERE id = ANY($1)
    ORDER BY id ASC
    FOR UPDATE
  `, pq.Array(obligationIDs))

  Retry Strategy:
    - On SQLSTATE 40P01 (deadlock detected): retry with exponential backoff (3x)
    - Base backoff: 100ms, multiplier: 2x (100ms → 200ms → 400ms)

Implementation (Dual-Layer):

  L1 (Redis — Fast Lookup):
    GET "idempotency:{key}" → cached response (TTL 24 hours)
    IF found → RETURN cached response
  
  L2 (PostgreSQL — Persistent):
    Column: payment_obligations.idempotency_key (UNIQUE)
    IF duplicate → conflict detected
    Store response body + status code in idempotency cache

  Timeout: 24 hours (idempotency cache expires_at = NOW() + INTERVAL '24 hours')

6.2 PAYMENT FLOW SECURITY (Payment Gateway as Source of Truth)
────────────────────────────────────────────────────────────────────────────────

PRINCIPLE (From PRD v6.0 — Out of Scope):
  E-Tix Flash TIDAK memiliki internal wallet atau ledger. Seluruh transaksi
  keuangan diproses melalui Payment Gateway. Sumber kebenaran (source of
  truth) untuk status pembayaran adalah:
    1. payment_obligations.status  (internal mirror)
    2. Payment Gateway API         (external authority)
  Keduanya direkonsiliasi via Webhook + Webhook Reconciliation Worker.

BOOKING HOLD FLOW (Seat Lock, Bukan Financial Escrow)

Step 1: Customer submits booking request
  - Seat di-lock di Redis bitmap (bit = 1) dengan TTL 180 detik
  - INSERT bookings (payment_status = 'PENDING')
  - INSERT payment_obligations (status = 'PENDING') per member (SPLIT) atau
    satu obligation (BULK)

Step 2: Payment Gateway initiation
  - Backend memanggil Payment Gateway API untuk membuat payment link
  - Simpan `external_transaction_id` ke payment_obligations
  - Kirim link ke setiap user (push/email/SMS)

Step 3: Webhook SUCCESS (authoritative)
  - Validasi signature HMAC dari Payment Gateway
  - Validasi idempotency (jika webhook duplikat → no-op)
  - UPDATE payment_obligations SET status = 'PAID' WHERE status = 'PENDING'
  - DB trigger `check_booking_payment_complete()` men-generate tickets

Step 4: Webhook FAILURE / TIMEOUT → Delayed Message (T+3 min)
  - Idempotent Lazy-Check pattern (LOGIC_FLOW v1.4 Section 4.3)
  - Jika masih PENDING: release seats di Redis (granular SETBIT),
    set payment_obligations.status = 'EXPIRED',
    refund via Payment Gateway untuk obligation yang sudah PAID,
    log ke admin_actions (action_type = 'FORCE_RELEASE_SEAT')

WEBHOOK RECONCILIATION WORKER (Fallback — LOGIC_FLOW v1.4 Section 4.5)
  - Berjalan setiap 10 menit
  - Cari payment_obligations.status = 'PENDING' dengan created_at > 10 menit
  - Panggil Payment Gateway API `GET /transactions/{external_transaction_id}`
  - Jika gateway_status = 'PAID' → UPDATE status = 'PAID' + log ke admin_actions
  - Jika gateway_status = 'FAILED' → UPDATE status = 'FAILED' + trigger rollback
  - Jika gateway_status = 'PENDING' → skip (tunggu webhook)

FINANCIAL INTEGRITY INVARIANTS

  ✅ Semua transaksi keuangan HARUS memiliki external_transaction_id yang
     dapat diverifikasi ke Payment Gateway.
  ✅ Tidak ada mutasi status pembayaran tanpa bukti webhook ATAU hasil
     rekonsiliasi ke Payment Gateway API.
  ✅ Semua aksi admin yang mengubah status pembayaran WAJIB dicatat ke
     admin_actions (immutable audit trail).
  ✅ Idempotency key mencegah double-charge.
  ✅ Sumber kebenaran eksternal (Payment Gateway) TIDAK PERNAH digantikan
     oleh perhitungan internal.

6.3 ADMIN FINANCIAL ACTIONS (Admin 2FA Required)
────────────────────────────────────────────────────────────────────────────────

ADMIN REVERSAL / MANUAL RECONCILIATION FLOW (API Contract Section 14.3)

  POST /admin/ledger/reverse
  Headers:
    - Authorization: Bearer <admin_token>
    - X-Admin-2FA-Token: <2fa_token>
  Body:

      reason, changes_before, changes_after, ip_address, user_agent
    - Idempotency key wajib untuk mencegah reversal ganda

7.4 CIRCUIT BREAKER (Graceful Degradation)
────────────────────────────────────────────────────────────────────────────────

FULL SPECIFICATION (From TDD v1.10 Section 7)

  | Parameter              | Value              | Description                    |
  |------------------------|--------------------|--------------------------------|
  | Interval               | 5 seconds          | Rolling window reset period    |
  | Failure Threshold      | 3 failures in 5s   | Opens circuit on threshold     |
  | Timeout                | 30 seconds         | OPEN duration before recovery  |
  | Half-Open MaxRequests  | 5                  | Test requests in HALF_OPEN     |
  | Recovery Condition     | 5 successful       | Closes circuit                 |
  | Fallback Action        | PostgreSQL FIFO    | Requests queue in DB queue     |
  | Recovery Worker        | DBQueueSyncWorker  | Drains DB queue when CLOSED    |

Implementation:

  cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "Redis",
    MaxRequests: 5,
    Interval:    5 * time.Second,
    Timeout:     30 * time.Second,
    ReadyToTrip: func(counts gobreaker.Counts) bool {
      failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
      return counts.Requests >= 3 && failureRatio >= 0.6
    },
  })

8.1 BEHAVIORAL INGRESS ENGINE (F001)
────────────────────────────────────────────────────────────────────────────────

2-STAGE PIPELINE (From LOGIC_FLOW v1.4 Section 2)

Stage 1 (Synchronous — <1ms):
  - Rate Limiter (Token Bucket) per IP/User ID

Stage 2 (Asynchronous — Background Worker):
  - Dynamic Score calculation based on:
    * Request interval (too fast → minus)
    * Click patterns (human vs bot)
    * Device fingerprint (known bot patterns)
  - Final Score = Base Score + Dynamic Score
  - If Final Score < 50 → CAPTCHA trigger + alert admin
  - If bot pattern detected → add to blacklist

FAN SCORE TIERS (From PRD v6.0 Section F001)

  | Tier   | Score Range | Priority Access               |
  |--------|-------------|-------------------------------|
  | TIER_1 | > 90        | VIP — First in queue          |
  | TIER_2 | 70-90       | Regular — Normal access       |
  | TIER_3 | < 70        | Low priority / CAPTCHA        |

8.2 QUEUE TOKEN (Anti-Replay)

QUEUE TOKEN LIFECYCLE

  2. Payload:

8.3 CAPTCHA MODAL (From HALAMAN v1.1 Section 3.2)
────────────────────────────────────────────────────────────────────────────────

TRIGGER CONDITIONS
  - Final Score < 50
  - Multiple failed booking attempts in short time
  - Suspicious device fingerprint

FLOW
  1. Client detects challenge required → shows CAPTCHA modal
  2. User solves challenge
  3. POST /queue/verify-captcha
     Body: { "challenge_id": "uuid", "solution": "traffic_lights" }
  4. Backend validates:
     - Solution correct?
     - Not expired?
     - Attempts < 3?
  5. If valid → return queue_token (JWT with jti)
  6. If invalid → increment failed attempts
     - 3 failures → 15 min lockout (Redis)

8.4 OFFLINE GATE QR VALIDATION
────────────────────────────────────────────────────────────────────────────────

Konteks:
  Gate staff dapat bekerja dalam mode offline (HALAMAN 11.3). Device scanner tetap harus
  memvalidasi Dynamic HMAC QR tanpa HTTP call ke backend.

Mekanisme:
  1. Saat sync awal (online), device gate staff menerima dan menyimpan:
     - Event Public Key (untuk verifikasi signature QR), ATAU
     - HMAC Secret Key temporer (jika skema QR menggunakan HMAC simetris).
  2. Key disimpan di secure local storage yang terenkripsi (Keychain/Keystore/IndexedDB terenkripsi).
  3. Saat offline, device:
     - Decode QR → ticket_id + signature.
     - Hitung ulang HMAC-SHA256 dengan key lokal + timestamp block tolerance (±30s).
     - Bandingkan signature secara lokal.
     - Jika valid → simpan scan log ke local queue (SQLite/IndexedDB) dengan scan_id UUIDv4.
     - Jika invalid → simpan log invalid untuk audit, tampilkan pesan INVALID.
  4. Saat koneksi pulih → batch sync via POST /gate/sync (max 500 scans per batch).
  5. Key lokal memiliki TTL dan dihapus setelah event selesai atau logout device.
  6. Secret key tidak pernah ditulis ke log, tidak pernah dikirim ke pihak ketiga.
  7. Conflict Resolution during Batch Sync (POST /gate/sync):
     - Jika ticket_id yang di-sync offline sudah berstatus 'USED' di database
       (akibat dipindai di gate lain secara offline):
       a. Record pindaian pertama yang masuk ke database diakui sebagai 'USED'.
       b. Record pindaian berikutnya yang masuk belakangan ditandai sebagai
          'ALREADY_USED' pada ticket_scans (sesuai scan_status_enum di DATABASE_SCHEMA v2.9)
          beserta device_id dan timestamp pindaian.
       c. Server mengembalikan response 200 OK dengan ringkasan status:
          {
            "synced": <N>,
            "duplicates": <M>,
            "failed": 0,
            "conflicts": [
              {
                "scan_id": "uuid-scan-late",
                "ticket_id": "uuid-ticket",
                "status": "ALREADY_USED",
                "winner_device_id": "uuid-device-first",
                "winner_scanned_at": "2026-09-10T19:15:23Z",
                "loser_device_id": "uuid-device-second",
                "loser_scanned_at": "2026-09-10T19:15:25Z"
              }
            ],
            "errors": []
          }
       d. Prinsip determinisme: record dengan scanned_at paling awal (earliest timestamp)
          dianggap pemenang. Jika timestamp identik (equal), tie-breaker = scan_id terkecil
          (lexicographic UUID ASC).
       e. Semua keputusan konflik dicatat ke ticket_scans untuk audit dan analytics EO.
       f. Gate staff pada device yang "kalah" tetap melihat notifikasi lokal
          "Duplicate scan detected — ticket already used at <winner_gate_id>".
       g. Notifikasi admin dikirim jika jumlah konflik > threshold (mis. 10 per batch).

Security Note:
  - Ini melengkapi F004 (Dynamic HMAC QR) dan F004b (Offline Sync).
  - Idempotency tetap dijaga via scan_id UUIDv4 + ON CONFLICT DO NOTHING.
  - Conflict resolution TIDAK menggunakan row-level lock secara global (hindari bottleneck);
    mengandalkan transactional check + conditional UPDATE dengan status guard
    (WHERE status = 'CONFIRMED' — sesuai ticket_status_enum DATABASE_SCHEMA v2.9).

13. INCIDENT RESPONSE PROCEDURES
================================================================================

13.1 INCIDENT CLASSIFICATION
────────────────────────────────────────────────────────────────────────────────

SEVERITY LEVELS

  CRITICAL (P0 — 15 min response)
    - Database down (service down)
    - Unauthorized access incident
    - Large payment fraud (> Rp 1,000,000)
    - Scalper bot bypass (mass ticket hoarding)
    Response: Full team, incident commander

  HIGH (P1 — 1 hour response)
    - Rate limiting not working (DoS risk)
    - Authentication failures (> 10%)
    - Multiple user account compromises
    - Circuit Breaker stuck OPEN
    Response: On-call engineer + team lead

  MEDIUM (P2 — 4 hour response)
    - Single account compromise
    - Minor data inconsistency
    - Performance degradation
    Response: Primary engineer assigned

  LOW (P3 — Business day response)
    - Cosmetic bugs
    - Documentation outdated
    - Non-critical monitoring gap
    Response: Add to backlog

13.2 INCIDENT RESPONSE WORKFLOW
────────────────────────────────────────────────────────────────────────────────

Step 1: DETECT & ALERT (Automated)
  - Alert fired (payment backlog, high error rate, etc.)
  - Slack notification to #incidents
  - PagerDuty alerts on-call engineer (P0-P1)

Step 2: ACKNOWLEDGE & ASSESS (5 min)
  - Incident commander notified
  - Gather initial information:
    * What is the issue?
    * Who is affected?
    * Financial impact?
  - Create incident ticket

Step 3: IMMEDIATE MITIGATION (15 min)
  For Critical Incidents:
    - Pause high-risk operations (if needed)
    - Collect logs (last 1 hour)
    - Take database snapshot (for forensics)
    - Notify customers (if service down)

Step 4: INVESTIGATION (30-60 min)
  - Root cause analysis
  - Query logs/metrics
  - Reproduce issue in staging
  - Identify fix

Step 5: IMPLEMENT FIX
  - Deploy hotfix (if coding required)
  - Coordinate with team
  - Verify fix in production

Step 6: VERIFY RESOLUTION (15 min)
  - Test affected functionality
  - Monitor metrics (error rate, latency)
  - Verify Payment Gateway reconciliation (if financial)
  - Customer communication (if needed)

Step 7: POST-INCIDENT (Next day)
  - Write incident report
  - Root cause analysis
  - Action items to prevent recurrence
  - Update runbooks/documentation

13.3 RUNBOOKS (Quick Reference)
────────────────────────────────────────────────────────────────────────────────

RUNBOOK: Payment Webhook Reconciliation Backlog

  Severity: HIGH

  1. Alert: payment_webhook_reconciliation_pending > 50 for > 15 min
  2. Check Pending Obligations:
     SELECT id, user_id, external_transaction_id, amount, created_at
     FROM payment_obligations
     WHERE status = 'PENDING'
     AND created_at < NOW() - INTERVAL '10 minutes'
     ORDER BY created_at ASC
     LIMIT 100;
  3. Verify Against Payment Gateway:
     - Login ke dashboard Payment Gateway
     - Cek status external_transaction_id satu per satu (sample 5-10)
  4. If Gateway Says PAID but internal PENDING:
     - Trigger manual reconciliation (Webhook Reconciliation Worker)
     - Log ke admin_actions (action_type = 'MANUAL_PAID')
  5. If Gateway Says FAILED:
     - Let worker update status to FAILED
     - Verify seats released in Redis
  6. Monitor backlog size until normal
  7. Post-mortem: why webhooks missed? (network, gateway, signature mismatch)

RUNBOOK: Redis Circuit Breaker Open

  Severity: HIGH

  1. Alert: circuit_breaker_state == 1 (OPEN)
  2. Check Redis status:
     redis-cli -h <host> PING
  3. If Redis down:
     - Backend automatically falls back to DB queue
     - DBQueueSyncWorker will drain queue when Redis recovers
  4. If Redis slow:
     - Check Redis metrics (latency, memory)
     - Consider scaling Upstash plan
  5. Monitor circuit breaker state for recovery
  6. Once CLOSED: verify queued bookings processed
  7. Post-mortem: why did Redis fail?

RUNBOOK: Mass Queue Token Replay Attempt

  Severity: CRITICAL

  1. Alert: token_blacklist_hits_total > 100 in 10 min
  2. Identify source IPs:
     SELECT ip_address, COUNT(*) FROM admin_actions
     WHERE action_type = 'BLACKLIST_IP'
     AND created_at > NOW() - INTERVAL '10 minutes'
     GROUP BY ip_address ORDER BY COUNT(*) DESC;
  3. Blacklist IPs:
     POST /admin/blacklist { type: 'ip', value: '...', reason: 'Replay attack' }
  4. Investigate if scalper bot:
     - Check device fingerprints
     - Check user accounts involved
  5. Add signatures to bot pattern blacklist
  6. Notify security team

RUNBOOK: Offline Multi-Device Scan Conflict Spike

  Severity: MEDIUM

  1. Alert: offline_scan_conflicts_total > 10 in single batch
  2. Investigate devices involved:
     SELECT scanner_device_id, gate_id, COUNT(*) FROM ticket_scans
     WHERE scan_status = 'ALREADY_USED'
     AND created_at > NOW() - INTERVAL '30 minutes'
     GROUP BY scanner_device_id, gate_id;
  3. Cross-check gate staff schedule — apakah ada gate duplikat / device tidak sah.
  4. Jika device tidak dikenal → revoke key lokal + force re-sync.
  5. Review ticket ownership log untuk indikasi fraud (screenshot QR dibagikan).
  6. Notify security team jika pola mencurigakan.

✅ Dynamic HMAC QR:
   - Signature: HMAC-SHA256(qr_secret_key, ticket_id | owner_user_id | 
                 timestamp_block)
   - timestamp_block = FLOOR(EXTRACT(EPOCH FROM NOW()) / 30)
   - Token tolerance: ±1 block (±30s) saat verifikasi (FASE 6)
   - QR data = base64(ticket_id + "|" + signature)
   - Redis cache: qr:{ticket_id} dengan TTL 35s

✅ QR Regeneration Worker:
   - Berjalan setiap 30 detik (ticker)
   - Update QR untuk semua tiket dengan status IN 
     ('CONFIRMED', 'RESALE_PENDING')
   - Store ke Redis (bukan DB) — high throughput, ephemeral

✅ Fallback PIN (FLAG #1 — PLAIN storage):
   - Generation: 12-char alphanumeric UPPERCASE (UUID-derived)
   - Storage: `tickets.fallback_pin` VARCHAR(12) UNIQUE — PLAIN
   - Single-use: fallback_pin_used BOOLEAN (default FALSE)
   - Setelah dipakai: fallback_pin_used = TRUE + fallback_pin_used_at = NOW()
   - Sent via SMS/Email saat ticket CONFIRMED (triggered by FASE 4's trigger 
     `check_booking_payment_complete`)
   - Response API: `fallback_pin: "A3F8K9L2M1N4"` (plain, sesuai API_CONTRACT)

✅ Ticket List (GET /tickets):
   - RLS enforced (only own tickets)
   - Filter status (CONFIRMED, USED, RESALE_PENDING, RESOLD)
   - Pagination

✅ Ticket Detail (GET /tickets/{ticket_id}):
   - Include event_name, section_name, seat_position, status, fallback_pin
   - Ownership check (JWT sub == tickets.owner_user_id)

✅ Dynamic QR Endpoint (GET /tickets/{ticket_id}/qr):
   - Return qr_data (base64), expires_at, refresh_in (28s)
   - Read from Redis (populated by worker)
   - If missing → regenerate on-demand + cache
   - Ownership check (JWT sub == tickets.owner_user_id)

✅ Assign Ticket (PATCH /tickets/{ticket_id}/assign):
   - Only current owner can assign
   - Only CONFIRMED status (bukan USED/RESOLD/CANCELLED)
   - Only ticket with is_assigned = FALSE (belum di-assign)
   - Validate target user status = 'ACTIVE'
   - Validate target NOT blacklisted
   - Idempotency: X-Idempotency-Key

3.1 FROM PRD v6.0 §F004 — DYNAMIC QR + FALLBACK PIN SPEC
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION:
  Membuat kode QR dinamis yang selalu berubah setiap 30 detik untuk mencegah 
  pencurian atau penggandaan tiket. Menyediakan Static Fallback PIN untuk 
  situasi darurat (HP mati, sinyal buruk).

INPUTS:
  - Ticket ID (UUID)
  - Current Owner User ID (UUID)
  - Secret System Key (qr_secret_key per ticket)

PROCESS — Primary (Dynamic HMAC QR):
  1. Sistem memuat timestamp server (blok 30 detik)
  2. Sistem menghitung HMAC-SHA256 dari gabungan:
     TicketID + OwnerID + Timestamp Block
  3. Sistem menampilkan string terenkripsi sebagai QR code
  4. QR Code berganti setiap 30 detik
  5. Screenshot/foto tidak valid (timestamp kadaluwarsa)

PROCESS — Secondary (Static Fallback PIN):
  1. Saat transaksi CONFIRMED, sistem generate 12-digit alfanumerik
  2. PIN dikirim via SMS + Email ke pemegang tiket
  3. PIN valid sepanjang hari acara, hanya bisa dipakai 1 kali
  4. PIN tidak bergantung pada koneksi internet
  5. Petugas gate bisa input PIN manual jika QR gagal
  6. Setelah PIN digunakan, sistem langsung tandai USED

OUTPUTS:
  - Rendered QR Code Image / Encrypted String Payload
  - Static Fallback PIN (12-digit alfanumerik) via SMS/Email

EDGE CASES:
  - Offline Event Gate Validation → gatekeeper pakai public key untuk 
    verifikasi signature lokal (FASE 6)
  - HP Mati Total → PIN manual entry (FASE 6)
  - PIN Bocor → single-use, tidak berbahaya
  - QR expired → regenerated otomatis (30s window)

3.3 FROM LOGIC_FLOW v1.4 §5 — FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

QR GENERATION FLOW (Background Worker — every 30s):

  Runs on ticker (every 30s):
    Step 1: SELECT id, owner_user_id, qr_secret_key FROM tickets 
            WHERE status IN ('CONFIRMED', 'RESALE_PENDING')
    Step 2: FOR EACH ticket:
      a. timestamp_block = FLOOR(EXTRACT(EPOCH FROM NOW()) / 30)
      b. payload = ticket_id + owner_user_id + timestamp_block
      c. signature = HMAC-SHA256(qr_secret_key, payload)
      d. qr_data = base64_encode(ticket_id + "|" + signature)
      e. SET "qr:{ticket_id}" = qr_data EX 35
    Step 3: UPDATE tickets SET last_qr_generated_at = NOW() (batch)

FALLBACK PIN GENERATION FLOW (triggered by FASE 4's trigger):

  Triggered when ticket is created (payment complete):
    Step 1: raw_pin = UPPER(SUBSTRING(REPLACE(gen_random_uuid(), '-', ''), 1, 12))
    Step 2: INSERT tickets dengan:
              fallback_pin = raw_pin (PLAIN — FLAG #1)
              fallback_pin_used = FALSE
    Step 3: Send raw_pin via SMS (Twilio) + Email (SendGrid)
            (worker: NotificationService)
    Step 4: Log dispatch event (NOT the PIN itself — header sanitization)

GET /tickets/{id}/qr FLOW:

  Handler:
    Step 1: Auth middleware (JWT required)
    Step 2: SELECT ticket WHERE id = {ticket_id}
    Step 3: Verify ticket.owner_user_id == JWT sub
              - If not → 403 FORBIDDEN
    Step 4: GET "qr:{ticket_id}" from Redis
              - If found → return cached (fast path)
              - If missing → regenerate on-demand:
                  a. Compute HMAC with current timestamp_block
                  b. SET "qr:{ticket_id}" = qr_data EX 35
                  c. Return
    Step 5: Compute refresh_in = 30 - (now % 30)
    Step 6: Return { qr_data, expires_at, refresh_in }

GET /tickets FLOW:

  Handler:
    Step 1: Auth middleware
    Step 2: SELECT tickets WHERE owner_user_id = JWT sub
              (RLS enforces ownership)
    Step 3: Optional filter by status (query param)
    Step 4: Pagination (page, limit)
    Step 5: Return list with event_name, section_name, seat_position, status

GET /tickets/{id} FLOW:

  Handler:
    Step 1: Auth middleware
    Step 2: SELECT ticket WHERE id = {ticket_id}
    Step 3: Verify ownership (JWT sub == owner_user_id)
              - If not → 403
    Step 4: JOIN event + section untuk names
    Step 5: Return detail (include fallback_pin PLAIN — FLAG #1)

PATCH /tickets/{id}/assign FLOW:

  Handler:
    Step 1: Auth middleware
    Step 2: X-Idempotency-Key required
    Step 3: SELECT ticket WHERE id = {ticket_id} FOR UPDATE
    Step 4: Verify ownership (JWT sub == owner_user_id)
              - If not → 403 FORBIDDEN
    Step 5: Verify status = 'CONFIRMED' 
              - If not → 409 CONFLICT
    Step 6: Verify is_assigned = FALSE 
              - If already → 409 CONFLICT
    Step 7: SELECT target user status + is_blacklisted
              - If not found → 404
              - If status != 'ACTIVE' → 422 TARGET_USER_INACTIVE_OR_SUSPENDED
              - If is_blacklisted → 422
    Step 8: UPDATE tickets SET:
              owner_user_id = target_user_id
              original_owner_user_id = current_owner_user_id
              is_assigned = TRUE
              updated_at = NOW()
            WHERE id = {ticket_id} AND is_assigned = FALSE
    Step 9: Check RowsAffected (0 → concurrent assign, return 409)
    Step 10: Return updated ticket

3.4 FROM TDD v1.10 §6.4 — IMPLEMENTATION FLOW SUMMARY (PSEUDOCODE ONLY)
────────────────────────────────────────────────────────────────────────────────

HMAC QR VERIFICATION HELPER (dipakai FASE 6, tapi generate di sini):

  Function VerifyDynamicQR(qrToken, secretKey):
    Step 1: Decode base64 → data
    Step 2: Split "|" → [ticketID, signature]
    Step 3: Parse ticketID as UUID
    Step 4: currentBlock = NOW().Unix() / 30
    Step 5: FOR block IN [currentBlock - 1, currentBlock, currentBlock + 1]:
              a. payload = ticketID + "|" + block
              b. expected = HMAC-SHA256(secretKey, payload)
              c. IF hmac.Equal(signature, expected):
                   RETURN (valid = true, ticketID)
    Step 6: RETURN (valid = false, error "invalid or expired")

QR REGENERATION WORKER:

  Function QRRegenerationWorker():
    ticker := time.NewTicker(30 * time.Second)
    FOR range ticker.C:
      ProcessAllTickets()

  Function ProcessAllTickets():
    Step 1: currentBlock = NOW().Unix() / 30
    Step 2: SELECT id, owner_user_id, qr_secret_key FROM tickets 
            WHERE status IN ('CONFIRMED', 'RESALE_PENDING')
    Step 3: Use Redis pipeline untuk batch SET:
              FOR EACH ticket:
                qr_data = generateQR(ticket, currentBlock)
                PIPE.SET "qr:{ticket_id}" qr_data EX 35
              PIPE.EXEC
    Step 4: Log: {count, duration_ms, timestamp_block}

FALLBACK PIN NOTIFICATION:

  Function SendFallbackPIN(ticket, user):
    Step 1: Compose message:
              "Your E-Tix Flash Fallback PIN: {fallback_pin}"
    Step 2: Send via SMS (Twilio) — queue
    Step 3: Send via Email (SendGrid) — queue
    Step 4: Log dispatch (NOT the PIN — grep verify)

3.6 FROM SECURITY_SPEC v1.4 §3.2, §8.3 — TICKET SECURITY
────────────────────────────────────────────────────────────────────────────────

SENSITIVE FIELDS (SECURITY_SPEC §3.2 asli — RESOLVED via FLAG #1):

  Foundation state (sebelum FLAG #1):
    - SECURITY_SPEC §3.2: `tickets.fallback_pin_hash | SHA-256 (hashed)`
    - LOGIC_FLOW §5.2: "Store hashed PIN (SHA-256)"

  Reality (DATABASE_SCHEMA v2.9 + API_CONTRACT v1.2):
    - Column: `fallback_pin VARCHAR(12)` — PLAIN
    - Response: `"fallback_pin": "A3F8K9L2M1N4"` — PLAIN

  Resolution (FLAG #1 — Opsi A):
    - Plain storage respected (schema truth)
    - Security mitigations:
      * DB encrypted at rest (Supabase AES-256)
      * RLS owner-only
      * 12-char alphanumeric (47-bit entropy — brute-force infeasible)
      * Single-use (fallback_pin_used)
      * Header sanitization (PIN NOT in logs)
      * Rate limit on verify (FASE 6)
    - Future improvement: hash migration to v1.1+ (requires schema amendment)

QR SECURITY:

  - HMAC-SHA256 (bukan SHA-256 plain)
  - Secret key per ticket (qr_secret_key, UUID v4)
  - Time-bound: timestamp_block (30s window)
  - Tolerance: ±1 block untuk clock skew
  - Redis TTL 35s (5s grace untuk network latency)
  - Screenshot protection: timestamp akan expire dalam ≤30s
  - No PII in QR (hanya ticket_id + signature)

PIN SECURITY:

  - 12-char alphanumeric UPPERCASE (36^12 ≈ 4.7 × 10^18 combos)
  - Single-use (fallback_pin_used)
  - Sent via SMS + Email (dual channel)
  - 47-bit entropy cukup untuk single-use token
  - Header sanitization (PIN never in logs)
  - Rate limit verify di FASE 6 (gate side)

HEADER SANITIZATION:

  - Authorization → [REDACTED]
  - Log tidak mengandung "eyJ"
  - Log tidak mengandung raw PIN (grep verify)

10.1 FLAG #1: FALLBACK PIN STORAGE ALIGNMENT (PLAIN TEXT VIA SCHEMA TRUTH)
────────────────────────────────────────────────────────────────────────────────

Konteks:
  Konflik 3-arah di foundation:
    - DATABASE_SCHEMA v2.9: `fallback_pin VARCHAR(12)` — PLAIN
    - API_CONTRACT v1.2 §10.1-10.2: response PLAIN "A3F8K9L2M1N4"
    - LOGIC_FLOW v1.4 §5.2: "Store hashed PIN (SHA-256)"
    - SECURITY_SPEC v1.4 §3.2: `fallback_pin_hash` — HASH

Verdict (Opsi A — APPROVED by Gemini):
  - PLAIN storage respected (DATABASE_SCHEMA truth)
  - Column name: `fallback_pin` (bukan `fallback_pin_hash`)
  - Response API: PLAIN (per API_CONTRACT)
  - Justifikasi teknis:
    * VARCHAR(12) tidak cukup untuk SHA-256 hex (64 char)
    * Amend schema → breaking G2 + regenerate FASE 0 (LOCKED)
    * Hierarchy: DATABASE_SCHEMA > API_CONTRACT > LOGIC_FLOW/SECURITY_SPEC
    * LOGIC_FLOW/SECURITY_SPEC dianggap documentation artifact

Security mitigations:
  - DB encrypted at rest (Supabase AES-256)
  - RLS owner-only
  - 12-char alphanumeric (47-bit entropy — brute-force infeasible)
  - Single-use (fallback_pin_used)
  - Header sanitization (PIN never in logs)
  - Rate limit verify di FASE 6

Traceability: FLAG #1 documented di Section 10 untuk audit trail.

Future work (v1.1+): migration ke SHA-256 hash butuh schema amendment 
(G2 breach) — catat di TECHNICAL_DEBT jika diperlukan.

10.2 NOTES UMUM
────────────────────────────────────────────────────────────────────────────────

- FASE 5 = fitur user-facing PERTAMA setelah auth. Kualitas UX penting, 
  tapi fokus utama security (QR + PIN).

- HMAC-SHA256 dengan per-ticket qr_secret_key. JANGAN pakai global secret 
  (kalau global key bocor, semua QR compromised).

- Timestamp block 30s = trade-off antara UX (refresh interval) dan 
  security (window). Screenshot expire dalam ≤30s.

- QR TTL di Redis: 35s (bukan 30s) — grace 5s untuk network latency + 
  clock skew antara client dan server.

- QR verifier juga dipakai di FASE 6 (Gate). Toleransi ±1 block untuk 
  handle edge case network latency.

- Fallback PIN PLAIN di DB (FLAG #1). 47-bit entropy cukup untuk 
  single-use token. Mitigations: encryption at rest, RLS, single-use, 
  log sanitization.

- Fallback PIN single-use: mark `fallback_pin_used = TRUE` saat 
  verification (FASE 6). FASE 5 hanya generate + send + display.

- Notification worker (SMS + Email) dispatch PIN saat ticket creation. 
  Ini hook dari FASE 4 trigger, tapi implementasinya di FASE 5.

- QRRegenerationWorker = goroutine ticker. BUKAN RabbitMQ consumer (karena 
  butuh periodic execution, bukan event-driven). Ini konsisten dengan TDD 
  §6.4.

- Ticket list grouping: client-side group by status (Active/Used/Resold). 
  Backend hanya return flat list.

- Assign ticket: atomic + RowsAffected check. Concurrent assign →

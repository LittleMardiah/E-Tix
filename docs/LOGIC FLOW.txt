1. EXECUTIVE SUMMARY & KEY PRINCIPLES
================================================================================

Dokumen ini menjelaskan **alur logika bisnis (business logic flow)** untuk E-Tix Flash.
Setiap flow di bawah ini merujuk pada:

- PRD v6.0-FINAL (F001-F006)
- DATABASE SCHEMA v2.9-FINAL (tabel, enum, trigger, RLS)

KEY PRINCIPLES (WAJIB DIINGAT):

| Principle | Description |
|-----------|-------------|
| **Atomicity** | Semua operasi yang melibatkan beberapa tabel atau wallet WAJIB atomic (ALL or NOTHING). |
| **Idempotency** | Semua operasi finansial WAJIB mendukung X-Idempotency-Key (L1 Redis + L2 PostgreSQL via payment_obligations.idempotency_key). |
| **Event-Driven** | Tidak ada polling untuk status payment. Webhook + Delayed Message Queue (RabbitMQ). |
| **Idempotent Lazy-Check** | Pesan delay TIDAK PERNAH dibatalkan. Worker cek status di T+3 menit dan memutuskan action. |
| **Circuit Breaker** | Jika Redis down > 100ms, sistem masuk Degraded Mode (fallback ke PostgreSQL FIFO). |
| **Deadlock Prevention** | Semua multi-row transaction WAJIB menggunakan ORDER BY id ASC. |
| **Single-Use Token** | Queue Token hanya valid untuk 1 kali penggunaan (cegah replay attack). |
| **Granular Bit Release** | Release bitmask per-kursi menggunakan SETBIT, tidak pernah overwrite seluruh string. |
| **Native Redis Bitmap** | F002 UNIFORM menggunakan GETBIT/SETBIT (0-based offset), BUKAN manipulasi string ASCII. |
| **Hashed Fallback PIN** | Fallback PIN disimpan dan dibandingkan sebagai SHA-256 hash (bukan plain-text). |

2. FLOW F001: BEHAVIORAL INGRESS & FAN-SCORE QUEUEING
================================================================================

2.1 OVERVIEW

F001 bertugas menyaring bot dan memberikan akses prioritas kepada fans loyal.
Alur ini menggunakan pendekatan 2-Stage Pipeline + Pre-Computed Base Score.

2.2 STATE DEFINITION (User Scoring)

| State | Description |
|-------|-------------|
| **BASE_SCORE** | Skor awal dihitung pra-acara (umur akun, verifikasi, riwayat pembelian). |
| **DYNAMIC_SCORE** | Skor tambahan dari perilaku real-time (interval request, pola klik). |
| **FINAL_SCORE** | BASE_SCORE + DYNAMIC_SCORE. |
| **TIER_1** | FINAL_SCORE > 90 → Priority access (VIP Fans). |
| **TIER_2** | FINAL_SCORE 70-90 → Normal access. |
| **TIER_3** | FINAL_SCORE < 70 → Access after Tier 1 & 2. |
| **BLACKLISTED** | IP/Device terdeteksi sebagai bot → Diblokir di Stage 1. |

2.3 SEQUENCE FLOW

┌─────────────────────────────────────────────────────────────────────────────┐
│                     F001: BEHAVIORAL INGRESS FLOW                          │
└─────────────────────────────────────────────────────────────────────────────┘

[PRE-FLASH SALE: Pre-Computation]
  │
  ├─> Sistem hitung BASE_SCORE dari users table:
  │    - Umur akun: (NOW() - created_at) / 365 hari → +10 poin per tahun
  │    - Email terverifikasi → +10 poin
  │    - Phone terverifikasi → +10 poin
  │    - Total purchases >= 1 → +10 poin
  │    - Total purchases >= 3 → +30 poin
  │    - Total purchases >= 5 → +50 poin
  │    - Simpan di Redis: "user:score:{user_id}:base"
  │
  └─> Selesai. Siap menerima request.

[USER REQUEST MASUK]
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ STAGE 1 (SYNCHRONOUS — Target < 1ms)                                      │
│ Berjalan di API Gateway / Golang Middleware                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. Rate Limiter (Token Bucket) cek limit per IP/User ID.                 │
│     └─> Jika exceeded → HTTP 429 + log warning.                           │
│                                                                             │
│  2. Validasi header dasar (User-Agent, Accept-Language).                  │
│                                                                             │
│  3. Cek blacklist IP di memory cache (diupdate dari Redis setiap 60s).   │
│     └─> Jika terdaftar → HTTP 403 + log "BLACKLISTED".                    │
│                                                                             │
│  4. Baca Base Score dari Redis.                                           │
│     └─> Jika tidak ada → default = 50 (new user).                         │
│                                                                             │
│  5. Baca Dynamic Score dari Redis (jika ada dari request sebelumnya).     │
│     └─> Jika tidak ada → 0.                                               │
│                                                                             │
│  6. Hitung Final Score = Base + Dynamic.                                  │
│     └─> Tentukan Tier:                                                    │
│         - > 90 → Tier 1 (Priority)                                        │
│         - 70-90 → Tier 2 (Normal)                                         │
│         - < 70 → Tier 3 (Low Priority)                                    │
│                                                                             │
│  7. Kirim metadata ke Message Broker (NATS/RabbitMQ) untuk Stage 2.      │
│     └─> Async, tidak blocking response.                                  │
│                                                                             │
│  8. Generate Queue Token (JWT) dengan payload:                            │
│     { user_id, tier, final_score, jti, expiry: NOW() + 5 minutes }       │
│     └─> FIXED v1.3: jti (JWT ID) untuk single-use guard.                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ STAGE 2 (ASYNCHRONOUS — Background Worker)                                │
│ Berjalan di Background Worker (subscriber Message Broker)                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. Worker menerima metadata dari queue.                                  │
│                                                                             │
│  2. Hitung Dynamic Score berdasarkan perilaku real-time:                  │
│     - Interval antar request (terlalu cepat → minus).                    │
│     - Pola klik (manusia vs bot).                                         │
│     - Device fingerprint (known bot pattern).                             │
│                                                                             │
│  3. Update Final Score = Base + Dynamic.                                  │
│     └─> Simpan di Redis: "user:score:{user_id}:dynamic" dengan TTL.      │
│                                                                             │
│  4. Jika Final Score < 50 → kirim notifikasi ke Admin + CAPTCHA trigger. │
│                                                                             │
│  5. Jika terdeteksi pola bot yang jelas → tambahkan ke blacklist.        │
│     └─> INSERT INTO blacklist (type='ip', value=..., reason='BOT_DETECTED')│
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

2.4 EDGE CASES & HANDLING

| Edge Case | Handling |
|-----------|----------|
| Redis down saat Stage 1 | Circuit Breaker → Degraded Mode: Rate limiting dilonggarkan, Base Score default 50, semua user dianggap Tier 2. |
| User baru tanpa Base Score | Default 50 → diproses sebagai Tier 3. Stage 2 akan update Dynamic Score. |
| Traffic spike > 50.000 RPS | Circuit Breaker → Virtual Waiting Room via WebSocket Cluster. |
| Bot detected di Stage 2 | INSERT INTO blacklist (type='device_fingerprint' atau 'ip'). Stage 1 akan memblokir request berikutnya. |

2.5 DATABASE TABLE REFERENCES

| Table | Operation |
|-------|-----------|
| users | SELECT base_score, total_purchases, first_purchase_at, last_purchase_at |
| blacklist | SELECT (check), INSERT (add bot) |
| Redis | SET/GET user score, TTL management, queue_token:used:{jti} |

3. FLOW F002: BITMASK MULTI-SEAT ATOMIC LOCKING — UNIFORM NATIVE REDIS BITMAP
================================================================================

3.1 OVERVIEW

F002 mengunci N-kursi secara atomic menggunakan operasi bitwise di Redis.
Denah kursi dipartisi per section untuk mengurangi konflik.
Mapping Seat ID ↔ Bit Position bersifat immutable setelah layout diterbitkan.

⚠️ CRITICAL — UNIFORM NATIVE REDIS BITMAP (FIXED v1.4):
- F002, F003, F006, dan Section 9.3 WAJIB menggunakan native Redis Bitmap (GETBIT/SETBIT).
- OFFSET: 0-based (posisi kursi 1 → offset 0).
- TIDAK PERNAH menggunakan manipulasi string ASCII pada key bitmap.

3.2 STATE DEFINITION (Seat & Booking)

| State | Description |
|-------|-------------|
| **AVAILABLE** | Bit = 0, kursi kosong. |
| **LOCKED** | Bit = 1, kursi sedang di-lock (TTL 3 menit). |
| **PENDING_SPLIT_PAY** | Kursi terkunci, menunggu pembayaran grup. |
| **CONFIRMED** | Sudah dibayar, tiket valid. |
| **RESALE_PENDING** | Sedang dalam proses resale. |
| **CANCELLED** | Dibatalkan. |
| **USED** | Sudah di-scan di gate. |

3.3 SEQUENCE FLOW

┌─────────────────────────────────────────────────────────────────────────────┐
│                    F002: BITMASK ATOMIC LOCKING FLOW                       │
└─────────────────────────────────────────────────────────────────────────────┘

[USER REQUEST: BOOK SEATS]
  │
  ├─> Input: Event ID, Section ID, Seat IDs [10,11,12,13], Queue Token
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. VALIDATE INPUT                                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│   - Validasi Queue Token (JWT signature & expiry).                        │
│   - FIXED v1.3: Validasi single-use token via Redis:                      │
│     SET "queue_token:used:{jti}" 1 NX EX 300                              │
│     └─> Jika return nil (token sudah dipakai) → HTTP 409 CONFLICT.       │
│   - Validasi Event masih dalam periode flash sale.                        │
│   - Validasi Section ID valid.                                            │
│   - Validasi semua seat position dalam range 1..total_seats.             │
│   - Validasi maksimum N = 10 (dari system_config.max_group_seats).       │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. EXECUTE REDIS LUA SCRIPT (ATOMIC — NATIVE BITMAP)                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   -- FIXED v1.4: UNIFORM NATIVE REDIS BITMAP                              │
│   -- Key: "seats:{event_id}:{section_id}:v{layout_version}"               │
│   -- Argument: ARGV[1] = JSON array of seat positions [10,11,12,13]       │
│   -- Argument: ARGV[2] = booking_id                                       │
│   -- Argument: ARGV[3] = JSON booking data                                │
│   -- CRITICAL: OFFSET 0-based (pos - 1)                                   │
│                                                                             │
│   local seats = cjson.decode(ARGV[1])                                    │
│                                                                             │
│   -- Step 1: Check all seats availability using GETBIT (0-based)         │
│   for i, pos in ipairs(seats) do                                          │
│     local bit_val = redis.call('GETBIT', KEYS[1], pos - 1)               │
│     if bit_val == 1 then                                                  │
│       return cjson.encode({status = 'CONFLICT', position = pos})         │
│     end                                                                   │
│   end                                                                     │
│                                                                             │
│   -- Step 2: Lock all seats using SETBIT                                   │
│   for i, pos in ipairs(seats) do                                          │
│     redis.call('SETBIT', KEYS[1], pos - 1, 1)                             │
│   end                                                                     │
│                                                                             │
│   -- Step 3: Store booking mapping with TTL 180 seconds                  │
│   redis.call('SET', 'booking:'..ARGV[2], ARGV[3], 'EX', 180)             │
│                                                                             │
│   return cjson.encode({status = 'SUCCESS', booking_id = ARGV[2]})        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. CREATE BOOKING RECORD (DB)                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   INSERT INTO bookings (                                                  │
│     id, event_id, section_id, leader_user_id,                            │
│     seat_positions, total_seats, total_amount,                           │
│     payment_mode, payment_status, expires_at                             │
│   ) VALUES (                                                              │
│     booking_id, event_id, section_id, user_id,                           │
│     '[10,11,12,13]', 4, total_amount,                                   │
│     payment_mode, 'PENDING', expires_at                                 │
│   );                                                                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 4. SEND DELAYED MESSAGE (F003)                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Kirim pesan ke RabbitMQ dengan x-delay = 3 menit:                       │
│   { type: 'RELEASE_SEAT_CHECK', booking_id: booking_id }                 │
│                                                                             │
│   Catatan: Pesan ini TIDAK PERNAH DIBATALKAN (Idempotent Lazy-Check).    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
[RETURN RESPONSE]
  │
  ├─> Booking ID, Seat Allocation Map, Expiry Timestamp
  │
  └─> User melihat timer 3 menit di layar.

3.4 EDGE CASES & HANDLING

| Edge Case | Handling |
|-----------|----------|
| Partial Seat Lock Conflict (1 dari 4 kursi sudah diambil) | Lua Script langsung rollback (tidak ada kursi yang di-lock). Return "Seats No Longer Available". |
| Redis Cluster Failure | Circuit Breaker → Degraded Mode: Semua request masuk waiting room FIFO (di PostgreSQL). |
| Immutability Violation (layout berubah di tengah) | Pencegahan: layout_version di sections dicek. Jika mismatch, tolak request. |
| TTL 180 detik habis (belum bayar) | Delayed Message worker di F003 mengeksekusi rollback (release bitmask granular via SETBIT). |
| Queue Token Replay Attack | Single-use guard via Redis SET NX. Token hanya valid 1 kali. |

3.5 DATABASE TABLE REFERENCES

| Table | Operation |
|-------|-----------|
| events | SELECT status, seat_layout_version |
| sections | SELECT total_seats, bitmask_key, layout_version |
| bookings | INSERT (booking record) |
| Redis | GETBIT/SETBIT (NATIVE BITMAP), SET booking mapping (with TTL), SET queue_token:used:{jti} |
| Message Broker | SEND delayed message (F003) |

4. FLOW F003: GROUP SPLIT-PAY EXECUTION ENGINE
================================================================================

4.1 OVERVIEW

F003 mengelola pembayaran grup dengan 2 mode: SPLIT dan BULK.
Menggunakan event-driven (webhook) + Delayed Message Queue (Idempotent Lazy-Check).
Tidak ada polling. Tidak ada pembatalan pesan di RabbitMQ.

4.2 STATE DEFINITION (Payment)

| State | Description |
|-------|-------------|
| **PENDING** | Belum dibayar. |
| **PAID** | Sudah dibayar (webhook received). |
| **EXPIRED** | TTL 3 menit habis, belum lunas. |
| **FAILED** | Payment gateway reject. |
| **REFUNDED** | Uang dikembalikan (setelah rollback). |
| **CANCELLED** | Booking dibatalkan. |

4.3 SEQUENCE FLOW — SPLIT MODE

┌─────────────────────────────────────────────────────────────────────────────┐
│                   F003: SPLIT MODE — PAYMENT FLOW                         │
└─────────────────────────────────────────────────────────────────────────────┘

[USER REQUEST: SPLIT MODE]
  │
  ├─> Booking ID sudah dibuat di F002
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. CREATE PAYMENT OBLIGATIONS                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   FOR EACH user IN group:                                                 │
│     INSERT INTO payment_obligations (                                     │
│       booking_id, user_id, seat_position, amount,                        │
│       payment_link, idempotency_key, status                              │
│     ) VALUES (                                                           │
│       booking_id, user_id, seat_pos, amount,                            │
│       gen_payment_link(), gen_idempotency_key(), 'PENDING'              │
│     );                                                                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. SEND NOTIFICATIONS (Async)                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Kirim link pembayaran ke setiap user via:                               │
│   - Push Notification (FCM)                                               │
│   - Email (SES/SendGrid)                                                  │
│   - SMS (Twilio/Wablas) — untuk Fallback PIN juga                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. WAIT FOR WEBHOOK (Event-Driven)                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   [CASE A: Webhook SUCCESS]                                               │
│   │                                                                        │
│   ├─> Payment Gateway kirim webhook ke /webhook/payment                   │
│   │                                                                        │
│   ├─> Validasi signature & idempotency key                               │
│   │   └─> Jika duplikat → return cached response (200 OK)               │
│   │                                                                        │
│   ├─> UPDATE payment_obligations SET status = 'PAID'                     │
│   │   WHERE id = obligation_id AND status = 'PENDING'                    │
│   │                                                                        │
│   ├─> Trigger check_booking_payment_complete()                           │
│   │   └─> Jika semua obligation PAID:                                    │
│   │       - UPDATE bookings SET payment_status = 'PAID'                  │
│   │       - Generate tickets (1 per obligation)                          │
│   │       - Set is_assigned = TRUE                                       │
│   │       - Generate QR secret key + Fallback PIN                        │
│   │                                                                        │
│   └─> Response: 200 OK                                                   │
│                                                                             │
│   [CASE B: Webhook FAILED / TIMEOUT]                                     │
│   │                                                                        │
│   ├─> Retry dengan exponential backoff (3x max)                         │
│   │   └─> Jika masih gagal → status FAILED                              │
│   │                                                                        │
│   └─> Admin notified via Slack/Email                                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 4. DELAYED MESSAGE WORKER (IDEMPOTENT LAZY-CHECK)                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Worker menerima pesan di T+3 menit:                                     │
│   { type: 'RELEASE_SEAT_CHECK', booking_id: booking_id }                 │
│                                                                             │
│   -- LAZY CHECK:                                                          │
│   SELECT payment_status FROM bookings WHERE id = booking_id;            │
│                                                                             │
│   IF status = 'PAID' THEN                                                │
│     → No-op (ACK pesan, tidak melakukan apa-apa)                        │
│   ELSIF status = 'PENDING' OR 'EXPIRED' THEN                            │
│     → Eksekusi rollback:                                                 │
│       1. Lock booking FOR UPDATE                                         │
│       2. Release seats in Redis (granular via SETBIT)                   │
│          └─> FIXED v1.4: UNIFORM native bitmap release                  │
│          └─> FOR EACH seat_pos IN booking.seat_positions:               │
│               redis.call('SETBIT', key, seat_pos - 1, 0)                │
│       3. UPDATE bookings SET payment_status = 'EXPIRED'                  │
│       4. UPDATE payment_obligations SET status = 'EXPIRED'              │
│          WHERE booking_id = booking_id AND status = 'PENDING'           │
│       5. Refund user(s) yang sudah bayar (via Payment Gateway refund)   │
│       6. INSERT INTO admin_actions (action = 'FORCE_RELEASE_SEAT')      │
│       7. Kirim notifikasi ke semua anggota: "Transaksi gagal"            │
│   END IF;                                                                │
│                                                                             │
│   Catatan: Pesan TIDAK PERNAH dibatalkan — worker selalu execute.        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

│   Setelah di-assign, anggota dapat mengelola tiket sendiri (F005).       │
│                                                                             │

4.5 WEBHOOK RECONCILIATION WORKER (Fallback)

┌─────────────────────────────────────────────────────────────────────────────┐
│                WEBHOOK RECONCILIATION WORKER                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Berjalan setiap 10 menit:                                               │
│                                                                             │
│   -- Cari transaksi PENDING yang sudah > 10 menit                        │
│   SELECT id, user_id, external_transaction_id, amount                   │
│   FROM payment_obligations                                               │
│   WHERE status = 'PENDING'                                              │
│   AND created_at < NOW() - INTERVAL '10 minutes';                       │
│                                                                             │
│   FOR EACH pending_transaction:                                          │
│     → Panggil Payment Gateway API untuk cek status pembayaran           │
│       GET /transactions/{external_transaction_id}                        │
│                                                                             │
│     IF gateway_status = 'PAID' THEN:                                    │
│       → UPDATE payment_obligations SET status = 'PAID'                  │
│       → Log ke admin_actions: "RECONCILED_PAYMENT"                      │
│     ELSIF gateway_status = 'PENDING' THEN:                             │
│       → Skip (tunggu webhook)                                           │
│     ELSE:                                                                │
│       → UPDATE payment_obligations SET status = 'FAILED'               │
│       → Trigger rollback:                                               │
│         1. Release seats in Redis (granular via SETBIT)                │
│            └─> FIXED v1.4: UNIFORM native bitmap release               │
│         2. UPDATE bookings SET payment_status = 'EXPIRED'               │
│         3. Kirim notifikasi ke user                                     │
│     END IF;                                                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

4.6 EDGE CASES & HANDLING

| Edge Case | Handling |
|-----------|----------|
| Webhook duplikat | Idempotency key → cache hit → return 200, no mutation. |
| Webhook hilang | Webhook Reconciliation Worker polling ke Payment Gateway setiap 10 menit. |
| Partial payment (1 dari 4 bayar) | TTL 3 menit habis → rollback semua kursi → refund otomatis ke user yang sudah bayar. |
| Double payment (user bayar 2x) | Idempotency key → tolak transaksi kedua. |
| Bulk Mode + Assign Ticket | Leader bisa assign tiket ke anggota kapan saja sebelum acara. |
| seat_position NULL di SPLIT mode | Trigger check_booking_payment_complete() akan RAISE EXCEPTION. Backend WAJIB memastikan seat_position terisi. |
| Granular bit release race condition | FIXED v1.4: Release per-bit via SETBIT, tidak pernah overwrite. |

│     'used_tickets', (SELECT used_tickets FROM ticket_stats),             │
│     'unused_tickets', (SELECT unused_tickets FROM ticket_stats),         │

9.1 IDEMPOTENCY PATTERN

┌─────────────────────────────────────────────────────────────────────────────┐
│                    IDEMPOTENCY PATTERN                                    │
└─────────────────────────────────────────────────────────────────────────────┘

[REQUEST MASUK dengan X-Idempotency-Key]
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. L1 Redis Cache (Fast — Primary)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│   GET "idempotency:{key}"                                                │
│   IF found → RETURN cached response                                      │
│   IF not found → Continue                                               │
└─────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. L2 PostgreSQL (Persistent — Fallback)                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│   -- Idempotency key disimpan di payment_obligations.idempotency_key    │
│   SELECT id FROM payment_obligations                                     │
│   WHERE idempotency_key = $key;                                         │
│                                                                             │
│   IF found → RETURN cached response (from Redis or re-query)            │
│   ELSE → Process request:                                                │
│     1. Generate idempotency_key                                          │
│     2. INSERT INTO payment_obligations (..., idempotency_key)           │
│     3. Store response in Redis: SET "idempotency:{key}" = response EX 86400│
│     4. RETURN response                                                   │
│                                                                             │
│   Catatan: L2 PostgreSQL menggunakan kolom idempotency_key di            │
│   payment_obligations sebagai referensi. L1 Redis adalah primary         │
│   storage untuk fast lookup.                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

12. EXCEPTION HANDLING MATRIX
================================================================================

| Exception | Trigger | Recovery |
|-----------|---------|----------|
| **Redis Down** | Redis cluster failure | Circuit Breaker → Degraded Mode (FIFO queue). Auto-recover when Redis up. |
| **Webhook Missing** | Payment gateway callback timeout | Reconciliation Worker polls PG every 10 min. |
| **Database Deadlock** | Concurrent transactions | Retry with exponential backoff (3x). ORDER BY id prevents. |
| **Payment Gateway Timeout** | PG API slow | Retry 3x with backoff. Fallback to manual reconciliation. |
| **Admin 2FA Failed** | Wrong OTP/Token | Rate limit: 3 attempts → 15 min lockout. |
| **Bulk Cancel Partial Failure** | Some refunds fail | Async worker retries. Admin notified. |
| **Payout API Failed** | Seller payout failed | Status = PENDING_PAYOUT. Admin manual reconciliation. |
| **Partial Seat Lock Conflict** | Another user took 1 seat | Lua script rollback all. User notified "Seats No Longer Available". |
| **Duplicate Webhook** | Same webhook received twice | Idempotency key → ignore duplicate. |
| **Expired Delayed Message** | TTL 3 min passed | Worker lazy-check: if PAID → no-op; if PENDING → rollback. |
| **User Already Paid (Double Charge)** | User paid 2x via different method | Idempotency key → second payment rejected. |
| **QR Expired** | QR not refreshed | User pulls to refresh. New QR generated. |
| **Fallback PIN Used Twice** | Someone tries same PIN | fallback_pin_used = TRUE → INVALID. |
| **Resale Race Condition** | Two buyers claim same resale | SELECT FOR UPDATE prevents double-claim. |
| **Resale Buyer Doesn't Pay** | Buyer claims but never pays | Reservation TTL 3 min → reset to PENDING. |
| **Queue Token Replay Attack** | Token reused within 5 min | Single-use guard via Redis SET NX → HTTP 409. |
| **Granular Bit Release Conflict** | Overwriting whole bitmap | FIXED v1.4: Use SETBIT per position, never overwrite. |
| **Fallback PIN Plain-text Exposure** | SQL injection or read replica leak | FIXED v1.4: Store and compare as SHA-256 hash. |
